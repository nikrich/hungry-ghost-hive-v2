# Phase 2.D — Multi-Worker Parallelism + Feature-Branch Integration

**Status:** Draft — pending implementation plan
**Date:** 2026-06-01
**Predecessors:** [Phase 2.A spec](2026-05-30-phase-2.a-tech-lead-and-worker-roles-design.md), [Phase 2.A verification runbook](../plans/2026-05-30-phase-2.a-verification-runbook.md)

## 1. Summary

Phase 2.A proved the architecture: tech-lead decomposes one requirement into a DAG of sized stories; manager dispatches by role; junior wrote real Go and pushed a commit. But it serializes — one subprocess at a time. Phase 2.D lifts that cap and adds the missing integration mechanism so chains can actually run to completion.

Three changes:

- **Manager spawn-fills up to `max_workers` concurrent workers** in a single tick + keeps a dedicated tech-lead slot warm (so planning never starves while workers are busy).
- **Feature-branch model**: tech-lead creates `feature/<slug>` on the bare remote per requirement; workers base their worktree off that feature branch, not `main`. Result: one requirement = one clean integration diff at the end.
- **New `hive merge "<story-title>"` CLI**: operator-driven merge of a worker's agent branch into the requirement's feature branch + flip story drawer to `merged`. Phase 2.C's future QA role will call the same primitive.

Verification produces 3 workers running concurrently on independent stories, each merged into a shared feature branch, with the parent requirement transitioning `decomposed → in-flight → complete`.

## 2. Goals & Non-goals

### Goals

- `max_workers` concurrent worker subprocesses, gated by config (default: 3) + dedicated tech-lead slot (1 fixed, not configurable for now).
- Tech-lead and workers can spawn in the same manager tick — planning isn't blocked by ongoing implementation.
- All work for a requirement integrates on a per-requirement feature branch. Operator gets a coherent diff at the end (`feature/<slug>` → `main`) rather than scattered commits.
- New `hive merge "<story-title>"` flips review → merged with a real git merge of agent branch → feature branch.
- Re-running the verification scenario produces concurrent worker spawns + a `feature/<slug>` branch with 3 merge commits on it.

### Non-goals

- **QA role / auto-review** — Phase 2.C. Operator drives `hive merge` manually for now; Phase 2.C just calls the same primitive from a QA worker.
- **Conflict resolution during merge** — `hive merge` refuses non-fast-forward + conflict cases and tells the operator to resolve manually.
- **Auto-integration of feature branch into main** — operator does this themselves via `gh pr create` or manual git ops.
- **Resource-aware dynamic concurrency** — hardcoded `max_workers` per workspace stays.
- **Multi-day reliability validation** — Phase 2.E.
- **Cross-requirement dependencies** — still scoped within one requirement.

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | Split concurrency cap: `max_workers` for workers + 1 dedicated tech-lead slot | Planning never starves; long-running senior stories don't block decomposition of new requirements |
| 2 | Manager **spawn-fills in one tick** — loops `while live_workers < max_workers && ready: spawn one` | Throughput-first; the 8-min tick cap has plenty of headroom; idle slots are wasted slots |
| 3 | Story prioritization: **oldest by `created_at`** | Naturally produces topological order since tech-lead emits stories in dep order |
| 4 | New `hive merge "<story-title>"` CLI: git-merges agent branch into the story's `feature_branch` + flips story drawer to `merged` | Operator-driven for now; Phase 2.C's QA role piggy-backs on the same primitive |
| 5 | Tech-lead creates per-requirement feature branch on decomposition | Stable target for all child stories; integration diff is the whole requirement, not scattered |
| 6 | Workers base their worktree off `origin/<feature_branch>`, not `origin/main` | Story B's worker can see story A's commits if A merged before B started |
| 7 | Manager's `depends_on=merged` check is unchanged — `hive merge` is what produces `merged` state | Same schema; same scheduling logic |
| 8 | Feature-branch slug derived from requirement title: lowercase, non-alphanumeric → `-`, truncate at 50 chars, `feature/` prefix, collision-suffix `-2`/`-3`/... | Human-readable; deterministic; tech-lead handles collisions |
| 9 | `hive merge` works on the canonical clone (`repos/<team>/`), not a worktree — temporary checkout, merge, push, then `git checkout -` | Single-threaded operation; race window with manager tick is small; revisit only if real workloads show it bites |
| 10 | Tech-lead and workers can spawn in the same tick; no per-tick spawn cap beyond live limits | Throughput; the 8-min tick cap is the safety net |
| 11 | `hive merge` is exact-match by story title, with `--dry-run` flag | Predictable; matches drawer schema where titles are unique within a requirement |
| 12 | Backward-compatible: stories without `feature_branch` set (legacy from P2.A) base off `main` | No migration required for old workspaces |

## 4. Data Model

Three drawer types add fields. One Go struct grows.

### `requirement` drawer (additions)

```yaml
---
type: requirement
status: pending | decomposed | in-flight | complete | blocked
title: <verbatim from inbox>
decomposed_into: [<story-title>, ...]
feature_branch: feature/<slug>           # NEW — set by tech-lead at decomposition time
created_at: <iso>
---
```

### `story` drawer (additions)

```yaml
---
type: story
status: pending | assigned | review | merged | blocked | abandoned
title: ...
team: ...
points: ...
depends_on: [...]
acceptance_criteria: [...]
parent_requirement: ...
feature_branch: feature/<slug>          # NEW — copied from parent requirement at creation
pr_url: ...
merged_at: <iso>                         # NEW — set by hive merge
---
```

### `Drawer` struct (additions)

```go
type Drawer struct {
    // ... existing fields ...

    // Phase 2.D — feature branch + merge timestamp
    FeatureBranch string `yaml:"feature_branch"`
    MergedAt      string `yaml:"merged_at"`
}
```

### Backward compatibility

Pre-2.D drawers don't have `feature_branch` set. Manager treats absent `feature_branch` as "base worktree off `main`" — exactly current Phase 2.A behavior. No migration required. New requirements after 2.D upgrade get the feature-branch model from the start.

### Feature branch slug rule

Tech-lead computes from requirement title:

1. Lowercase
2. Replace non-alphanumeric runs with `-`
3. Trim leading/trailing `-`
4. Truncate at 50 chars (so total path including `feature/` stays well under filesystem limits)
5. Prepend `feature/`
6. Check bare remote for collision; if present, append `-2`, `-3`, etc.

Example: `"Add /healthz endpoint to the test API"` → `feature/add-healthz-endpoint-to-the-test-api`

## 5. Skill Changes

### `assets/skills/tech-lead.md` — feature branch creation

New step **between Decompose and Emit stories**:

```markdown
### 1.5. Create the feature branch on the remote

Compute the slug from the requirement title (rules in spec §4).

Check for collision:
```bash
git -C repos/<team> ls-remote --heads origin "feature/<slug>"
```

If a hit, append `-2`/`-3`/etc. until unique.

Create the branch on the remote (from origin/main):
```bash
git -C repos/<team> fetch origin main --quiet
git -C repos/<team> push origin origin/main:refs/heads/feature/<slug>
```

Record the resulting slug for use in step 2 (every story drawer gets this `feature_branch` field) and step 3 (the requirement drawer's `feature_branch` field).
```

Step 2 (Emit stories) frontmatter list gains: `feature_branch: <slug>`.

Step 3 (Update requirement) fields list gains: `feature_branch: <slug>`.

Worked example updated to mention the feature branch creation as step 0.

### `assets/skills/manager.md` — spawn-fill loop + tech-lead slot

**Diff 1 — MUST block** rewrites the single-subprocess constraint:

```markdown
- **YOU MUST** spawn up to `max_workers` concurrent worker subprocesses + AT MOST 1 concurrent tech-lead. Read `max_workers` from `.hive/config.yaml`.
```

**Diff 2 — Live-count semantics** split into TWO counters:

```markdown
Compute counts:
- `live_workers` = .hive/agents/<id>/worker.pid files whose role is junior/intermediate/senior AND `kill -0 <pid>` returns 0
- `live_tech_leads` = same but for role=tech-lead
```

**Diff 3 — Step 3a (tech-lead spawn) gate:** allows worker spawn in same tick

```markdown
#### 3a. Spawn priority 1 — tech-lead

If `live_tech_leads == 0` AND at least one requirement has `status=pending`:
- Pick the oldest pending requirement
- Spawn the tech-lead (recipe unchanged from Phase 2.A)
- DO NOT exit the tick — continue to step 3b (workers may also spawn this tick)
```

**Diff 4 — Step 3b (worker spawn) becomes a loop:**

```markdown
#### 3b. Spawn workers up to max_workers (loop)

While `live_workers < max_workers` AND there are ready stories:
- Pick the oldest ready story (by `created_at`)
- Determine role from `story.points` (1-3 → junior, 5 → intermediate, 8/13 → senior)
- Compute base branch:
  - If `story.feature_branch` set → use it
  - Else (legacy P2.A story) → use `main`
- Create worktree based on the feature branch:
  ```bash
  git -C repos/<team> fetch origin <base_branch> --quiet
  git -C repos/<team> worktree add ../<team>--<role>-<id> -b agent/<team>--<role>-<id> origin/<base_branch>
  ```
- Write context.md (now includes `Base branch: <base_branch>` so the worker knows where it forked from)
- Spawn the worker subprocess (unchanged)
- File agent-state drawer; update story to `assigned`
- Increment `live_workers` for the loop condition
```

**Diff 5 — Reap step parent-requirement transition:** unchanged from P2.A logic.

**Diff 6 — Diary format adds breakdown:**

```
manager  tick-end  spawned=<roles-list> reaped=<n> live_workers=<n>/<max> live_tech_leads=<n>/1 pending_reqs=<n> ready_stories=<n> waiting_stories=<n>
```

`spawned=<roles-list>` is e.g. `tech-lead,junior,junior` if this tick spawned all three. `none` if nothing spawned.

**Diff 7 — After-tick checklist** gains:
- Did I compute `live_workers` and `live_tech_leads` separately?
- If I spawned workers, did I base each one's worktree on `story.feature_branch` (or `main` for legacy)?

### `junior.md` / `intermediate.md` / `senior.md` — no logic change

Workers just read `context.md` which now mentions the base branch. Git ops (commit + push) work identically — `git push origin agent/<branch>` doesn't care about the base.

`tasks/creating-a-pr.md` skill unchanged.

## 6. `hive merge` CLI

New cobra subcommand. ~150 LOC total across two new files.

### File layout

```
cmd/hive/
└── merge_cmd.go        # NEW — cobra wiring (~30 LOC)

internal/cli/
├── merge.go            # NEW — RunMerge implementation (~80 LOC)
└── merge_test.go       # NEW — 3 unit tests (~70 LOC)
```

### API

```go
package cli

type MergeOptions struct {
    WorkspaceRoot string
    StoryTitle    string  // exact-match against story drawer titles
    DryRun        bool
}

func RunMerge(opts MergeOptions) error
```

### Operation

```text
1. Resolve workspace + read .hive/config.yaml for team list.
2. Walk <MEMPALACE_ROOT>/wings/hive/rooms/stories/ — find drawer with title == opts.StoryTitle.
3. Validate the story drawer:
   - status MUST be "review" (else: error "story is <status>, cannot merge")
   - feature_branch MUST be set (else: error with legacy hint)
   - team MUST exist in config.yaml's teams (else: error)
   - assigned_to MUST be set (need it to reconstruct agent branch name)
4. Find the agent-state drawer for the assignee — read its role to reconstruct:
   agent_branch = "agent/" + team + "--" + role + "-" + assigned_to
5. If --dry-run: print the git plan and exit 0 (no state change).
6. Run git ops in repos/<team>:
     git fetch origin --quiet
     ORIG_HEAD=$(git rev-parse --abbrev-ref HEAD)
     git checkout <feature_branch>
     git pull origin <feature_branch> --quiet
     git merge --no-ff --no-edit origin/<agent_branch>
     git push origin <feature_branch>
     git checkout "$ORIG_HEAD"
7. On any git failure (conflict, non-FF, remote rejection):
     - DO NOT update the drawer
     - Restore $ORIG_HEAD if not already done
     - Print: "merge failed: <git error>. Resolve manually with:
                git checkout <feature_branch> && git merge origin/<agent_branch> && git push
                Then update the story drawer directly OR re-run hive merge."
     - Return non-zero
8. On success:
     - Update story drawer via mempalace_update_drawer:
         status = merged
         merged_at = <iso-now>
     - Print: "Merged origin/<agent_branch> into origin/<feature_branch>"
     - Print: "Story \"<title>\" → merged"
     - Print: "Next manager tick (~60s) will pick up dependent stories whose deps are now satisfied."
```

### CLI wiring

```go
// cmd/hive/merge_cmd.go
package main

import (
    "github.com/nikrich/hungry-ghost-hive-v2/internal/cli"
    "github.com/nikrich/hungry-ghost-hive-v2/internal/paths"
    "github.com/spf13/cobra"
)

func init() {
    var dryRun bool
    cmd := &cobra.Command{
        Use:   "merge \"<story-title>\"",
        Short: "Merge a story's agent branch into its parent requirement's feature branch",
        Long:  `Merge the worker's agent branch into the requirement's feature branch + flip story.status to "merged". The story must be in "review". The agent branch is reconstructed from the story's assigned_to + role. Phase 2.C's QA role will call this same primitive.`,
        Args:  cobra.ExactArgs(1),
        RunE: func(c *cobra.Command, args []string) error {
            ws, err := paths.FindWorkspaceRoot(".")
            if err != nil {
                return err
            }
            return cli.RunMerge(cli.MergeOptions{
                WorkspaceRoot: ws,
                StoryTitle:    args[0],
                DryRun:        dryRun,
            })
        },
    }
    cmd.Flags().BoolVar(&dryRun, "dry-run", false, "print planned git operations without running them")
    rootCmd.AddCommand(cmd)
}
```

## 8. Verification Gate

### Test setup

Standard bare-remote pattern (see Phase 1.4 / 2.A runbooks). Workspace at `/tmp/hive-verify-ws`, bare remote at `/tmp/hive-verify-bare`.

### Test requirement (crafted for independence)

```sh
hive add-req "Add three doc updates to the test API repo:
1. README.md should get a new ## Quick Start section above the existing content.
2. README.md should get a new ## Endpoints section at the very bottom listing /version.
3. A CHANGELOG.md file should be created (it doesn't exist yet) with a single line: '- initial scaffold'.

Each of these is independent of the others — they touch different files (or distant sections of the same file) and have no shared logic."
```

This is crafted so the tech-lead can plausibly emit 3 independent stories (`depends_on: []` on all 3).

### Phase 2.D PASS criteria

| # | Check | How to verify |
|---|---|---|
| 1 | Tech-lead creates a feature branch on the bare remote | `git -C /tmp/hive-verify-bare branch -a` shows `feature/<slug>` |
| 2 | Requirement drawer has `feature_branch` populated | inspect drawer |
| 3 | Each story drawer has `feature_branch` set (same as requirement) | inspect drawers |
| 4 | Tech-lead decomposes into ≥2 independent stories (`depends_on: []` on each) | inspect drawers — at least 2 with empty deps |
| 5 | **In a single tick, manager spawns multiple workers (≥2 concurrent)** | mid-tick `ps aux` shows multiple `claude --print --system-prompt-file *.md` processes; manager.log shows `spawned=junior,junior,...` |
| 6 | Worker worktrees are based on the feature branch, not main | `git log agent/<branch> ^main` shows commits only on the agent branch |
| 7 | After all workers exit at `review`, operator runs `hive merge "<title>"` for each | each call succeeds; story drawer flips to `merged`; bare remote feature branch advances |
| 8 | `hive merge` git ops succeed against the bare remote | `git -C /tmp/hive-verify-bare log feature/<slug>` shows merge commits |
| 9 | After all stories merge, parent requirement transitions to `complete` (next manager tick) | inspect requirement drawer; `hive status` |
| 10 | `hive merge` refuses a story not in `review` | manually try to merge a `pending` story; expect refusal with clear error |
| 11 | New diary fields (`live_workers=N/max`, `live_tech_leads=N/1`) present | read diary drawer |

### Stretch (bonus, not required)

- All 3 PRs produce non-conflicting diffs (the test requirement is crafted for this)
- `hive merge --dry-run "<title>"` prints planned git operations without state change
- Tick that spawns 3 workers completes in <3 min (per-spawn overhead is bounded)

### Anti-PASS

- Manager spawns one worker at a time despite multiple ready stories (didn't parallelize)
- `hive merge` accepts a `pending` story (status guard missing)
- Workers commit on top of `main` instead of `feature/<slug>` (base branch wrong)
- `hive merge` flips drawer to `merged` even when git push fails (no atomicity)

## 9. Open Risks

| Risk | Mitigation |
|---|---|
| Manager tick that spawns 3 workers takes too long (approaches 8-min cap) | Per-spawn overhead is ~10-20s (mempalace ops + worktree add + nohup); 3 spawns ~60s on top of normal tick. Headroom is fine; bump cap if needed. |
| Two concurrent workers commit to the same files (shouldn't happen — independent stories) but tech-lead emits non-independent stories anyway | Tech-lead's prose insists on DAG; if it emits a cycle or conflicting deps, manager will stall those stories (deps never become merged). Operator-detectable via `hive status`. |
| `hive merge` race with manager tick (manager creates worktree from main while merge has temporary checkout) | Race window is short (~5-10s); manager `git worktree add` uses `origin/<branch>` not the local checkout state, so the local HEAD being temporarily on the feature branch is irrelevant. Acceptable. |
| Feature branch slug collision after `-2`/`-3` | Tech-lead skill enforces uniqueness check before push; collisions on `-9+` likely never happen for one workspace |
| Mempalace `mempalace_add_drawer` calls happen concurrently from multiple processes (tech-lead + workers all writing drawers) | mempalace gateway serializes its own writes; single MCP server per workspace; no expected races. If this bites, surface it in verification and design a queue. |
| Worker writes to story drawer (assigned/review) while manager reads it (scheduling check) | mempalace reads/writes are isolated per MCP call; no shared memory; stale reads at worst result in one extra tick of latency. Acceptable. |
