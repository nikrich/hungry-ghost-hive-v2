# Phase 1.2 — Workspace-Local Memory + Skill Bug Fixes

**Status:** Draft — pending implementation plan
**Date:** 2026-05-28
**Predecessors:** [`2026-05-27-architecture-design.md`](2026-05-27-architecture-design.md) (Phase 0), [`2026-05-28-phase-1.1-skill-hardening-design.md`](2026-05-28-phase-1.1-skill-hardening-design.md) (Phase 1.1), [`2026-05-28-phase-1.1-verification-runbook.md`](../plans/2026-05-28-phase-1.1-verification-runbook.md) (Phase 1.1 verification)

## 1. Summary

Phase 1.1 verification revealed three structural issues that together blocked the designed happy path:

1. **Memory was tied to the user's personal capstone-memory installation**, not to the workspace — wings written through `mempalace_add_drawer` ended up in ChromaDB only because hive's wing names weren't allowlisted in the shared mempalace's policy gateway.
2. **Worker subprocesses died immediately** because the manager skill spawned them with cwd inside the worktree, where claude's sandbox refused to read workspace-root paths.
3. **Abandoned stories silently stuck** at `assigned` with no live worker — no recovery logic.

Phase 1.2 addresses all three:

1. Memory moves to **workspace-local `.hive/memory/`** — owned by the workspace, no allowlist constraints, no coupling to anyone's personal palace. `hive init` bootstraps mempalace gateway via `pip install --user mempalace` if missing.
2. Workers spawn with **`cwd=workspace root`**; the junior skill `cd`s into its worktree as step 0. Context file remains a persistent artifact.
3. The manager reaps abandoned workers (story still `assigned` when the worker dies) and **re-pends the story with `retry_count++`**, escalating after 3 attempts.

With these fixes, the file-based `hive status` design from Phase 0 works as originally intended: writes through `mempalace_add_drawer` land as `.md` files under `.hive/memory/wings/hive/rooms/<room>/`, and the Go CLI reads them directly.

## 2. Goals & Non-Goals

### Goals

- **Workspace-local memory.** Each workspace's memory lives at `<workspace>/.hive/memory/`. Moving the workspace moves the memory.
- **Zero-step user setup.** `hive init` is the only command the user runs to bootstrap; mempalace gateway is installed automatically if needed.
- **Worker subprocesses actually do work.** Spawn cwd fixed; junior cd's in; context file is still written as a debug artifact.
- **No silent stuck stories.** Abandoned stories are detected, retried up to 3 times, then escalated with a drawer for human review.
- **`hive status` shows what's actually in memory.** Structured drawer writes land on disk; CLI reads from disk.

### Non-goals

- Embedding the mempalace gateway in the hive binary (defer to Phase 2+ if needed for non-capstone users)
- Sidecar-shipping a compiled mempalace binary with hive releases
- Reading the user's `~/.claude.json` for mempalace MCP config — Phase 1.1 added this but Phase 1.2 makes it irrelevant. The discovery helper stays in the codebase but is no longer called by `RunInit`.
- The `hive-<workspace-slug>` wing-naming convention from Phase 0 (collapsed to fixed wing `hive`)
- Multi-workspace coordination — each workspace is fully isolated
- Phase 2 scope: full role set, tech-lead decomposition, QA flow

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | Workspace-local memory at `<workspace>/.hive/memory/` | User-stated requirement; removes coupling to personal palace; workspace is portable |
| 2 | `hive init` ensures mempalace: prefer `uv tool install mempalace` if `uv` is on PATH (cleaner, faster, isolated); otherwise `python3 -m pip install --user mempalace` | Zero-step setup. Python 3 is universal on dev machines. Mempalace owns its own packaging on PyPI. |
| 3 | One fixed wing per workspace, named `hive` | Workspace IS the boundary; no naming collision possible. Phase 0's slug-based wing name is pointless namespacing in a workspace-local model. |
| 4 | Worker spawn `cwd=workspace root`; junior `cd`s into its worktree as step 0 | Phase 1.1 verification finding: claude sandbox in worktree cwd couldn't reach workspace-root `.hive/agents/<id>/context.md`. This fix preserves the context.md artifact. |
| 5 | Re-pend abandoned stories with `retry_count++`; escalate at retry_count >= 3 | Worker dies between `assigned` and `review` → silently stuck. Manager checks story status on reap; revert if abandoned. Bounded by N=3 cap. |

### Verification items (resolve during implementation)

- Confirm the PyPI package name is `mempalace` (could be `mempalace-gateway` or a different name). If different, use the actual name; spec stays correct in intent.
- Confirm the mempalace `.mempalace/config.yaml` schema for allowlist (assumed shape: `allowlist: [hive]`). If different, follow what mempalace expects.

## 4. Workspace Layout

Only `.hive/` changes; `.claude/skills/` and `repos/` are unchanged from Phase 1.1.

```
<workspace>/
├── .hive/
│   ├── config.yaml              # unchanged
│   ├── inbox/                   # unchanged
│   ├── .gitignore               # NEW: contains "memory/"
│   ├── memory/                  # NEW: workspace-local mempalace data
│   │   ├── wings/
│   │   │   └── hive/            # single fixed wing
│   │   │       └── rooms/
│   │   │           ├── requirements/
│   │   │           ├── stories/
│   │   │           ├── agents/
│   │   │           ├── escalations/
│   │   │           └── findings/
│   │   ├── index/
│   │   │   └── chroma/          # derived; mempalace rebuilds as needed
│   │   └── .mempalace/
│   │       └── config.yaml      # allowlist = [hive]
│   ├── watchdog.pid             # unchanged
│   ├── manager.pid              # unchanged
│   ├── manager.log              # unchanged
│   ├── watchdog.log             # unchanged
│   └── agents/                  # unchanged
│
├── .claude/
│   ├── skills/                  # unchanged from P1.1
│   ├── settings.local.json      # unchanged
│   └── mcp.json                 # MODIFIED: always workspace-local; auto-detect bypassed
│
└── repos/                       # unchanged
```

### `.claude/mcp.json` shape (always written by `hive init`)

```json
{
  "mcpServers": {
    "mempalace": {
      "command": "<absolute python3 path>",
      "args": ["-m", "mempalace_gateway.server"],
      "env": {
        "MEMPALACE_ROOT": "<absolute path to workspace>/.hive/memory"
      }
    }
  }
}
```

`<absolute python3 path>` is resolved at `hive init` time via `which python3` and stored as an absolute path. `MEMPALACE_ROOT` is the absolute path to the workspace's `.hive/memory/`.

### `.hive/memory/.mempalace/config.yaml` shape

```yaml
allowlist:
  - hive
```

(Schema to be confirmed against upstream mempalace docs during implementation. If different, follow upstream.)

### Notable consequences

- `.hive/memory/` is gitignored by default. Workspaces that want memory tracked can `git add -f .hive/memory/` or remove the entry from `.hive/.gitignore`.
- The workspace cannot be moved between machines without re-running `hive init` (absolute paths in mcp.json). Same caveat as Phase 1.1.
- Multiple workspaces on one machine each have their own `.hive/memory/` and their own mempalace gateway process when claude is invoked there. They don't share state.

## 5. Lifecycle (`hive init` is the only meaningfully-changed command)

Flow:

```
1. Validate flags. Refuse if .hive/ exists.
2. Write .hive/config.yaml. Create .hive/inbox/.
3. Ensure mempalace gateway is installed:
   a. Try `python3 -c "import mempalace_gateway"`. If exit 0, skip to (e).
   b. If `uv` is on PATH: `uv tool install mempalace` (preferred — faster, no global pollution).
   c. Else: `python3 -m pip install --user mempalace`.
   d. Re-check the import. If still failing, print a clear actionable error and exit non-zero.
   e. Determine the absolute python command (via `which python3`); record for use in step 8.
4. Create .hive/memory/ skeleton:
   - mkdir -p .hive/memory/wings/hive/rooms/{requirements,stories,agents,escalations,findings}
   - mkdir -p .hive/memory/index
   - mkdir -p .hive/memory/.mempalace
   - Write .hive/memory/.mempalace/config.yaml with allowlist = [hive].
5. Write .hive/.gitignore containing "memory/" + a newline.
6. Write .claude/skills/* from embedded assets (unchanged from P1.1).
7. Write .claude/settings.local.json from embedded asset (unchanged).
8. Write .claude/mcp.json with workspace-local config:
   - command = <python from step 3e>
   - args = ["-m", "mempalace_gateway.server"]
   - env.MEMPALACE_ROOT = <absolute path>/.hive/memory
9. Non-bare local repo warning for each team (unchanged from P1.1).
10. Print: "Workspace initialized. Memory at .hive/memory/. Run `hive add-req \"...\"` then `hive run` to start."
```

### Behavioral deltas table

| Step | P1.1 behavior | P1.2 behavior |
|---|---|---|
| `hive init` | Auto-detects mempalace MCP from `~/.claude.json`; falls back to placeholder + warning | Installs mempalace if missing; writes workspace-local mcp.json pointing at `.hive/memory/` |
| First tick (with a requirement in inbox) | Manager wrote drawers to ChromaDB only — wing wasn't allowlisted | Drawers written as `.md` files in `.hive/memory/wings/hive/rooms/<room>/`; visible to `hive status` |
| Worker spawn | Spawned with cwd inside worktree → sandbox rejected workspace-root file reads → worker died | Spawned with cwd=workspace root; junior cd's in; context.md readable |
| Worker dies abandoned | Story stuck at `assigned`, no recovery | Story reverted to `pending`, `retry_count` incremented; at 3 → `blocked` + escalation drawer |
| `hive status` | Showed zero counts (no on-disk drawers) | Shows real counts from the on-disk wings tree |

## 6. Skill File Changes

### `assets/skills/manager.md` — three diffs

**Diff 1: Wing name.** All references to `hive-<workspace-slug>` become just `hive`. ~6 lines affected.

**Diff 2: Worker spawn cwd.** Replace the current step 2 spawn block:

```bash
cd repos/<team>--junior-<id>
nohup claude --print --permission-mode acceptEdits "You are agent <id>. Read .hive/agents/<id>/context.md ..." > /dev/null 2>&1 &
WORKER_PID=$!
cd -
echo $WORKER_PID > .hive/agents/<id>/worker.pid
```

with (spawned from workspace root, no cd):

```bash
nohup claude --print --permission-mode acceptEdits "You are agent <id>. Your worktree is at repos/<team>--junior-<id>. Read .hive/agents/<id>/context.md, then invoke the hive-v2-junior skill. Begin." > /dev/null 2>&1 &
WORKER_PID=$!
echo $WORKER_PID > .hive/agents/<id>/worker.pid
```

**Diff 3: Re-pend logic in step 3 (Reap exited workers).** Replace the current reap block with the abandonment-detection logic described in §3 decision 5. Specifically:

- On worker death, find the agent-state drawer (room `agents`) and read its `current_story`.
- Look up the story drawer (room `stories`).
- If `story.status` is `review` or `merged` → agent completed; mark agent-state `exited/completed`.
- If `story.status` is `assigned` → agent abandoned the story:
  - If `story.retry_count < 3`: revert story to `pending`, bump `retry_count`, mark agent-state `exited/abandoned`.
  - If `story.retry_count >= 3`: set story `blocked`, file `escalation` drawer (title: `story <title> exhausted 3 retries`; body: agent IDs + session paths from prior attempts), mark agent-state `exited/abandoned`.
- Best-effort worktree cleanup; remove `.hive/agents/<id>/`.

### `assets/skills/junior.md` — one diff

Add a new step 0 in the Procedure section:

```markdown
### 0. Enter your worktree

Your spawn cwd is the workspace root. The manager's prompt told you the worktree path. Before doing anything else:

\`\`\`bash
cd repos/<team>--junior-<YOUR_ID>
\`\`\`

All subsequent commands operate inside the worktree. References to `.hive/agents/<YOUR_ID>/context.md` are now at `../../.hive/agents/<YOUR_ID>/context.md`.
```

Renumber existing steps 1-7 → 1-8 (insert at the top). Update step 1's `cat` path to use the new relative location.

### `assets/skills/tasks/*` — no changes

`creating-a-pr.md` and `filing-a-finding.md` unchanged.

### Tests strategy

- **`createMemoryDir`**: pure file-system work, fully unit-testable.
- **`ensureMempalace` check path**: stub a fake `python3` on PATH that prints success → assert no install is attempted.
- **`ensureMempalace` install path**: NOT unit-tested (would need to mock `pip`/`uv` invocations). Verified during T6 manual e2e.
- **End-to-end `RunInit`**: assert the new `.hive/memory/wings/hive/rooms/*` subdirs exist + `.claude/mcp.json` contains the expected absolute paths.

## 8. Verification Gate

Re-run the verification scenario from `2026-05-28-phase-1.1-verification-runbook.md` against the Phase 1.2 binary. Phase 1.2 PASS criteria:

- `hive init` produces `.hive/memory/` with the expected tree
- `hive init` installs mempalace (or no-ops if already installed); workspace `.claude/mcp.json` points at workspace-local memory
- Manager spawns worker; worker reads context.md without sandbox errors
- Worker actually opens a PR (test repo must be bare-remote for this — runbook clarifies the setup)
- Drawers visible BOTH via `mempalace_list_drawers` MCP call AND as `.md` files at `.hive/memory/wings/hive/rooms/<room>/`
- `hive status` shows non-zero counts matching the on-disk drawers
- Force-killing a worker mid-tick: next tick reverts story to `pending`, increments `retry_count`. Third forced kill produces `story.status=blocked` + an `escalation` drawer.

## 9. Out of scope (this spec)

- Bundling or embedding mempalace (defer)
- Cross-machine workspace portability (mcp.json contains absolute paths)
- Phase 2 features (tech-lead decomposition, full role set, QA review, multi-agent parallelism, real-remote integration tests via GitHub)
- Removing the `discoverMempalaceMCP` helper from Phase 1.1 — stays in the codebase as dead code for now; remove in a later cleanup pass if it's still unused

## 10. Open risks

| Risk | Mitigation |
|---|---|
| Public mempalace isn't on PyPI under the name `mempalace` | Verify during implementation; use the real package name; if there's no public package, escalate as a Phase 1.3 problem (might require shipping a sidecar after all) |
| Mempalace's `.mempalace/config.yaml` schema differs from assumed `allowlist: [hive]` | Verify during implementation; follow upstream schema |
| Mempalace gateway behaves differently when MEMPALACE_ROOT points at a freshly-created empty dir | Verify during T6 — mempalace's init flow should handle this. If not, add a "warm up" call during `hive init`. |
| Workers still die for other reasons we haven't seen yet | Phase 1.2's re-pend logic + retry cap means at worst we escalate after 3 attempts; we'll see the failure mode in escalation drawers |
| Mempalace gateway can't run two parallel processes against different roots on the same machine | Verify during T6; if it's a singleton, we have a bigger architectural problem and need to escalate |
