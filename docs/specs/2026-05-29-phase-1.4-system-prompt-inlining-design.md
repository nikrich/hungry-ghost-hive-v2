# Phase 1.4 — `--system-prompt-file` Inlining

**Status:** Draft — pending implementation plan
**Date:** 2026-05-29
**Predecessors:** [Phase 1.3 spec](2026-05-28-phase-1.3-tick-reliability-design.md), [Phase 1.3 verification runbook](../plans/2026-05-29-phase-1.3-verification-runbook.md)

## 1. Summary

Phase 1.3 verification surfaced a deeper problem than the spec anticipated: the manager process **never invoked the workspace-local `hive-v2-manager` skill at all** during a 5-minute hang. The session log showed 0 skill invocations and 10 exploratory Bash commands (`ls ~/.claude/skills/`, `find / -maxdepth 5 ...`, etc.). Prose imperatives at the top of the skill (added in P1.3) had no effect — the model simply didn't reach the skill body.

Phase 1.4 changes the architecture: instead of asking claude to "invoke the hive-v2-manager skill," the watchdog passes the skill content **as claude's system prompt** via `--system-prompt-file`. The manager IS the manager because the system prompt says so — no discovery cycle, no orientation phase, no way for the model to wander.

The same pattern applies to worker spawns: the manager's Bash recipe spawns junior subprocesses with `--system-prompt-file ../../.claude/skills/junior.md` instead of relying on skill invocation.

Two file changes (`internal/watchdog/watchdog.go` + `assets/skills/manager.md`), ~10 LOC total.

## 2. Goals & Non-Goals

### Goals

- Manager drives forward to inbox drain + drawer writes + worker spawn within a normal tick — verifiable by mempalace tool calls in the session log, not just Bash exploration.
- Workers spawn the same way and successfully reach at least `cat .hive/agents/<id>/context.md`.
- Re-run of the verification scenario produces on-disk drawers + a worker process + ideally a commit in the bare test remote.

### Non-goals

- Conditional `--bare` (still deferred; may revisit as perf optimization)
- `hive upgrade-config` command (still deferred)
- Removing `discoverMempalaceMCP` dead code (still deferred)
- Modifying skill content structurally — manager.md and junior.md stay as-is; they already have the MUST/MUST NOT + numbered-procedure structure that makes them suitable as system prompts.
- Stripping the YAML frontmatter from the skill files when used as system prompts — the model can tolerate leading YAML as inert prose.
- Phase 2 feature expansion (tech-lead, QA, full role set).

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | `--system-prompt-file` (replaces default system prompt) — NOT `--append-system-prompt-file` | P1.3 already showed that adding more prose on top of the default doesn't stop exploration. Replacing is more decisive: the model has nothing else to do but the procedure. Manager.md is self-sufficient enough to stand alone. |
| 2 | Inline both the manager AND the worker (junior) | Same exploration risk on both sides; doing both in one phase is zero extra cost and yields a complete verification rather than a partial one. |
| 3 | Watchdog passes `<absolute workspace path>/.claude/skills/manager.md`; manager skill's worker spawn recipe constructs the absolute path at runtime via `$(pwd)/...` or equivalent | Absolute paths are stable across cwd changes (worker spawns happen from the manager's cwd, which is the workspace root). Relative paths break when the worker process inherits a different working dir. |
| 4 | User prompt becomes a one-line trigger ("Do one tick now." for manager; "You are agent <id>. ... Begin." for worker) | The system prompt holds the procedure. The user message only kicks off the loop. Keeps the user-side prompt small and uninteresting. |
| 5 | Skill content stays as-is — no structural changes | The MUST/MUST NOT block, numbered procedure, success example, and after-tick checklist are all useful as system-prompt material. Frontmatter YAML at the top is harmless filler. |

## 4. Implementation Surface

| File | Change | ~LOC |
|---|---|---|
| `internal/watchdog/watchdog.go` | In `runOneTick`: replace the `opts.ManagerPrompt` positional arg with `--system-prompt-file <abs path to .claude/skills/manager.md>` + a short fixed positional `"Do one tick now."` | +5 / -2 |
| `assets/skills/manager.md` | Update the worker-spawn Bash recipe in step 2 (and the matching example in the success block): add `--system-prompt-file ${WORKSPACE_ROOT}/.claude/skills/junior.md` to the `nohup claude --print` invocation. Shorten the user prompt to a one-line trigger. | +6 / -4 |

Total: ~11 LOC delta. No new files, no new packages, no new commands.

### Watchdog code shape

```go
managerSkillPath := filepath.Join(opts.WorkspaceRoot, ".claude", "skills", "manager.md")
cmd := exec.Command(
    opts.ClaudeBinary,
    "--print",
    "--permission-mode", "acceptEdits",
    "--system-prompt-file", managerSkillPath,
    "Do one tick now.",
)
```

`opts.ManagerPrompt` is no longer used as the user prompt. We keep the `ManagerPrompt` field on Options for now (avoids a breaking change to the Options struct) but stop reading it.

### Manager skill worker-spawn recipe (replacement)

The current recipe (before P1.4):

```bash
nohup claude --print --permission-mode acceptEdits "You are agent <id>. Your worktree is at repos/<team>--junior-<id>. Read .hive/agents/<id>/context.md, then invoke the hive-v2-junior skill. Begin." > /dev/null 2>&1 &
```

Replacement (after P1.4):

```bash
nohup claude --print --permission-mode acceptEdits \
  --system-prompt-file "$(pwd)/.claude/skills/junior.md" \
  "You are agent <id>. Worktree: repos/<team>--junior-<id>. Read .hive/agents/<id>/context.md and begin." \
  > /dev/null 2>&1 &
```

Differences:
- Adds `--system-prompt-file "$(pwd)/.claude/skills/junior.md"` (the manager's cwd IS the workspace root, so `$(pwd)` gives the right absolute path)
- Drops "invoke the hive-v2-junior skill" from the user prompt (the system prompt IS the skill now)
- Slightly shorter user prompt overall

## 5. Verification Gate (P1.4 exit)

Re-run the P1.3 verification scenario (bare remote + workspace init + add-req + hive run). P1.4 PASS requires:

| Check | P1.3 result | P1.4 expected |
|---|---|---|
| Manager skill content is what claude operates against | ❌ 0 skill invocations; ignored | ✅ system prompt = manager.md; no invocation needed |
| Manager invokes mempalace tools (not just `Bash ls`) | ❌ 10 exploratory Bash, 0 mempalace calls | ✅ session log shows `mempalace_add_drawer`, `mempalace_list_drawers`, etc. |
| Drawers appear on disk in `wings/hive/rooms/*` | ❌ none | ✅ at least requirements + stories + agents |
| Worker process spawned | ❌ never reached | ✅ `.hive/agents/<id>/` exists at some point + worker.pid file |
| Worker reads its context.md | ⚠️ untested | ✅ verifiable from worker's own session log |
| Tick completes inside 8min budget | ❌ 5min SIGKILL | ✅ typically under 2-3 min with no exploration; bound by 8min |
| `manager.log` non-empty | ✅ in P1.3 when claude emitted | ✅ same |
| `hive status` returns counts matching drawers | ✅ counts (zero in P1.3 because nothing was filed) | ✅ non-zero post-tick |

Stretch goal: worker actually commits and pushes to the bare remote. Bonus, not required for PASS.

If after P1.4 the manager STILL doesn't invoke mempalace tools — e.g., reads the system prompt but treats it as suggestions — escalate to a deeper investigation. Possible levers:
- `--effort low` or `--model haiku` to discourage chatty exploration
- Conditional `--bare` for API-key users (separately addresses hook overhead)
- Strip frontmatter YAML so the system prompt opens with `# Hive Manager — One-Tick Skill\n## YOU MUST...` instead of `---\nname: hive-v2-manager\n...`

## 6. Open risks

| Risk | Mitigation |
|---|---|
| `--system-prompt-file` with the manager.md as-is causes claude to lose default tool-use guidance | Manager.md is already explicit about which tools to use (`mempalace_add_drawer`, `mempalace_update_drawer`, Bash, etc.). If subtle behaviors break we'll see it in verification and add a small "use these tools as needed" preamble. |
| Worker spawn passes `$(pwd)/.claude/skills/junior.md` but `$(pwd)` is something different at spawn time | The manager skill explicitly requires cwd to be the workspace root throughout its tick. Bash sub-shells inherit cwd from the manager. Risk is low; we'll see it in verification if it bites. |
| The YAML frontmatter at the top of manager.md confuses claude when used as system prompt | Empirically unlikely (claude handles mixed prose fine). If it does, easy follow-up: have the watchdog strip the frontmatter when reading the file. |
| The model now follows the system prompt obediently but does something unexpected because the procedure has bugs we didn't notice | Most likely real risk. Verification will surface it. Iterate the skill content in a later micro-fix if needed — manager.md is already pretty battle-tested in design, just never actually run end-to-end. |
