# Phase 2.A — Tech-Lead Decomposition + Full Worker Role Set

**Status:** Draft — pending implementation plan
**Date:** 2026-05-30
**Predecessors:** [Phase 1.4 verification runbook](../plans/2026-05-29-phase-1.4-verification-runbook.md) (foundation works end-to-end; junior is the only worker role)
**Concrete reference:** [The junior's 2026-05-29 blocker finding](../../) for `"Do a full rewrite to golang"` — a worked example of the decomposition shape this phase formalizes.

## 1. Summary

Today the manager hardcodes "every requirement = one 3-point story for the junior." That's why the junior could not handle `"Do a full rewrite to golang"` — there's no role that can decompose, and no role to handle stories larger than what a junior can do.

Phase 2.A introduces decomposition and the full worker role set:

- **`tech-lead.md`** (new role): every requirement is decomposed by a tech-lead into N sized story drawers with `depends_on` (DAG) and explicit `acceptance_criteria`.
- **`intermediate.md`** (new role): handles 5-point stories.
- **`senior.md`** (new role): handles 8- and 13-point stories.
- **`junior.md`** (updated): still handles 1-3 point stories; now self-checks against `acceptance_criteria` before committing.
- **`manager.md`** (updated): drains inbox into requirement drawers (no more 1:1 story shortcut); spawns tech-lead for any undecomposed requirement; spawns a worker by role based on `story.points`; respects `depends_on` (only schedules stories whose deps are `merged`).
- **`drawers.Drawer`** struct adds `DependsOn`, `AcceptanceCriteria`, `ParentRequirement`, `DecomposedInto`, `CurrentRequirement` fields.

Verification gate is a single requirement that produces a 3+ story DAG covering all three worker-role sizes, and that requirement actually runs to completion across multiple ticks.

## 2. Goals & Non-Goals

### Goals

- Every requirement passes through a `tech-lead` before any worker runs.
- Tech-lead produces a DAG of sized stories (Fibonacci 1-13) with explicit acceptance criteria.
- Manager dispatches each story to the correct role based on points (1-3 → junior, 5 → intermediate, 8+ → senior).
- Stories only run when their `depends_on` are all `merged`.
- Junior workers self-check against `acceptance_criteria` before committing.
- Verification: a multi-story requirement actually completes end-to-end across multiple roles.

### Non-goals

- **Multi-worker parallelism** — single subprocess at a time is preserved. Phase 2.D (next, by design) lifts this cap. All Phase 2.A schema and scheduling decisions are parallel-friendly so 2.D is a small lift.
- **QA review flow** — Phase 2.C. Today stories flip directly to `review` when a worker opens a PR, and the operator merges. After 2.C, QA reviews and flips to `merged`.
- **Multi-day reliability validation** — Phase 2.E.
- **Tech-lead reading the team repo** — locked at "requirement text only" (Q4). User-side discipline to write detailed requirements.
- **Tech-lead reading prior `findings` for cumulative learning** — deferred; noise control is its own design problem.
- **Re-decomposition mid-run** — a story is decomposed once at requirement arrival; if a story is too big later, the worker files a blocker finding (the existing Phase 1 mechanism).
- **Cycle detection in the Go layer** — tech-lead's skill says "form a DAG, never a cycle"; manager doesn't enforce.
- **Backward-incompatible changes** — Phase 1 stories without `depends_on` are treated as "no deps, ready"; the migration is graceful.

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | Tech-lead spawns on every requirement | Predictable architecture; one extra tick of latency on trivial requirements is noise for a multi-day system |
| 2 | Tech-lead emits a **DAG** of story drawers, each with `depends_on: [<story-title>]` | Matches how real software decomposition works (the junior's blocker finding produced exactly this shape); makes 2.D's parallelism a small lift |
| 3 | Tech-lead estimates Fibonacci points (1, 2, 3, 5, 8, 13); **all sizes run** (1-3 junior, 5 intermediate, 8+ senior) | Phase 2.A includes all three worker roles, so nothing sits on ice. Story drawer schema unchanged from the original Phase 0 design. |
| 4 | Tech-lead reads **only the requirement text** | User-side discipline (write detailed requirements); fastest tick; no repo-walk exploration overhead |
| 5 | Each story has an explicit `acceptance_criteria: [<testable conditions>]` field | First-class contract between tech-lead → worker → (future) QA; not parse-by-convention prose |
| 6 | Manager treats `depends_on` as "satisfied" only when dep `status == merged` | Strict; `review` and `assigned` can flip back; `merged` is the only guaranteed terminal success state |
| 7 | At most **one** subprocess at a time (tech-lead OR any worker, never both) | Same scheduling discipline as Phase 1.4; Phase 2.D lifts |
| 8 | Worker-role differentiation lives in skill **prose** (persona, scope expectations, escalation thresholds) — same underlying mechanics (cd into worktree, read context, commit, push, file outcome) | Tests whether Opus actually behaves differently with different personas in its system prompt. If not, we collapse to a single "worker" role in a later refactor. Worth knowing now. |
| 9 | Reorder of per-tick steps: **drain → reap → spawn**. Reap moves before spawn so a just-finished tick frees the slot for the next role. | Previously drain → spawn → reap. With Phase 2.A's "one subprocess at a time" gate, reap-first is required for the slot accounting to make sense. |

## 4. Data Model

### `story` drawer (modified — new fields)

```yaml
---
type: story
status: pending | assigned | review | merged | blocked | abandoned
title: <short imperative summary; unique within parent_requirement>
team: <team-name>
points: 1 | 2 | 3 | 5 | 8 | 13
depends_on: [<story-title>, ...]              # NEW; empty list = no deps
acceptance_criteria:                          # NEW; ≥1 testable condition
  - "<condition>"
parent_requirement: <requirement-title>       # NEW; back-pointer for traceability
assigned_to: <agent-id> | null
retry_count: 0
created_at: <iso>
updated_at: <iso>
pr_url: <url> | null
---

# <story title>

<2-5 sentences of intent / why; acceptance_criteria are in the field above, not here>
```

### `requirement` drawer (modified — small)

Gains a `decomposed_into` field set by the tech-lead on exit, and a new `decomposed` status value.

```yaml
---
type: requirement
status: pending | decomposed | in-flight | complete   # 'decomposed' and 'in-flight' are new transitions
decomposed_into: [<story-title>, ...]                  # NEW
created_at: <iso>
title: <verbatim from inbox first line>
---

<original inbox text>
```

Status transitions:
- `pending` → set when manager drains inbox
- `decomposed` → set by tech-lead on exit, with `decomposed_into` populated
- `in-flight` → set by manager when ≥1 child story is non-pending
- `complete` → set by manager when ALL child stories are `merged`

### `agent-state` drawer (modified — small)

`role` grows three new values. Tech-lead has no worktree.

```yaml
---
type: agent-state
role: tech-lead | junior | intermediate | senior      # tech-lead, intermediate, senior are NEW
status: live | exited
exit_reason: completed | abandoned | escalated
worktree: <path> | null                                # null for tech-lead (no worktree needed)
current_requirement: <title> | null                    # NEW; set for tech-lead only
current_story: <title> | null                          # set for workers; null for tech-lead
---
```

### `internal/drawers/drawers.go` — `Drawer` struct additions

```go
type Drawer struct {
    // ... existing fields (Title, Status, Type, Points, Team, AssignedTo, ...) ...

    // NEW for Phase 2.A:
    DependsOn           []string `yaml:"depends_on"`
    AcceptanceCriteria  []string `yaml:"acceptance_criteria"`
    ParentRequirement   string   `yaml:"parent_requirement"`
    DecomposedInto      []string `yaml:"decomposed_into"`
    CurrentRequirement  string   `yaml:"current_requirement"`
}
```

All optional (zero value = absent). Drawers without these fields parse cleanly (backward compatible with Phase 1).

### Story title as dependency identifier

`depends_on` arrays use **story titles**, not drawer IDs:

- Tech-lead emits stories one at a time via `mempalace_add_drawer`; doesn't know the new drawer's ID until after the call.
- Tech-lead skill enforces "story titles are unique within a `parent_requirement`."
- Tradeoff: renaming a story breaks all dependents. Acceptable for now.

## 5. Skill Changes

### `assets/skills/tech-lead.md` — NEW

Frontmatter:
```yaml
---
name: hive-v2-tech-lead
description: Use ONLY when invoked as the hungry-ghost-hive-v2 tech-lead. Decomposes ONE requirement into N sized story drawers with depends_on + acceptance_criteria. Reads only the requirement text — does not browse the team repo.
---
```

Body (load-bearing sections):

- **YOU MUST / YOU MUST NOT:**
  - YOU MUST decompose exactly one requirement and exit.
  - YOU MUST NOT use Edit, Write, or MultiEdit tools. Only `mempalace_*` MCP and Bash for reading context.
  - YOU MUST NOT spawn workers — only the manager does that.
  - YOU MUST NOT read the team repo or run `ls`/`find` outside of `.hive/`. Decompose based on the requirement text alone.
  - YOU MUST emit ≥ 1 `story` drawer via `mempalace_add_drawer`.
  - YOU MUST set `points` to a Fibonacci value (1, 2, 3, 5, 8, 13).
  - YOU MUST set `acceptance_criteria` to a list of ≥ 1 testable condition per story.
  - YOU MUST update the requirement drawer to `status=decomposed` with `decomposed_into=[<story titles>]` before exiting.

- **Procedure:**
  1. Read your context: `cat ../../.hive/agents/<YOUR_ID>/context.md` (contains requirement drawer ID + verbatim text).
  2. Decompose into the smallest number of stories that fully cover the requirement. For trivial requirements emit ONE story with points=1 or 2.
  3. For each story, in dependency order, call `mempalace_add_drawer` with full frontmatter (`type=story`, `status=pending`, `title`, `team`, `points`, `depends_on`, `acceptance_criteria`, `parent_requirement`).
  4. Update the requirement drawer (`mempalace_update_drawer`): `status=decomposed`, `decomposed_into=[<titles>]`.
  5. Update your own agent-state drawer: `status=exited`, `exit_reason=completed`.
  6. Diary: `mempalace_diary_write "tech-lead  decomposed  requirement=<title> stories=<N>"`

- **Sizing guidance:**
  - 1 point: trivial (add a comment, update a link, bump a version)
  - 2 points: small focused change (add a flag, add a single field with tests)
  - 3 points: standard atomic story (add an endpoint with one happy-path test)
  - 5 points: mid-complexity (touch 2-3 files; some structural judgment expected)
  - 8 points: complex (cross-cutting; needs design judgment; multiple files)
  - 13 points: large (consider whether this should be further decomposed; only emit if genuinely cohesive)

- **Acceptance criteria style guide:**
  - Each criterion is a testable assertion or observable post-condition.
  - Imperative: "README.md begins with '// HELLO'", "`go test ./...` passes", "PR opened against `main`".
  - Avoid soft language: "looks good", "is clean" → QA's job to interpret later.

- **After-decomposition checklist** (read before exit):
  - Did every story have ≥ 1 acceptance criterion?
  - Did dependencies form a DAG (no cycles, no references to titles that don't exist)?
  - Are story titles unique within this requirement?
  - Did the requirement drawer get the `decomposed_into` update?

### `assets/skills/junior.md` — UPDATED

Insert new step between Implement and Commit:

```markdown
### N+1. Self-check against acceptance criteria

Before committing, read your story drawer's `acceptance_criteria` list. For each:

- Testable assertion (e.g., `go test ./... passes`): run it and confirm.
- Observable post-condition (e.g., `README.md begins with '// HELLO'`): `cat`/`grep` and verify.
- If you cannot verify ANY criterion, do NOT commit a partial fix:
  - File a finding via `tasks/filing-a-finding.md` describing what's blocked.
  - Set your agent-state `exit_reason=escalated` and exit.

Only proceed to commit + push + PR if ALL criteria pass.
```

Update "After completion checklist" to include: "Did I verify each acceptance criterion?"

Same procedure as junior (cd into worktree, read context, implement, self-check, commit, push, PR, file outcome). Differences are in persona prose:

- Frontmatter:
  ```yaml

  name: hive-v2-intermediate
  description: Use ONLY when invoked as the hungry-ghost-hive-v2 intermediate developer. Handles 5-point stories — mid-complexity changes touching 2-3 files with some structural judgment.

  ```

### `assets/skills/senior.md` — NEW

Same procedure as junior + intermediate. Persona:

- Frontmatter:
  ```yaml
  ---
  name: hive-v2-senior

  ---
  ```
- Persona block: "You are a senior developer. The story you're given involves design judgment. Consider the implications of your change for adjacent systems. Write tests AND consider edge cases. If the change has architectural consequences, document them in the PR description so reviewers can understand the trade-offs."

### `assets/skills/manager.md` — UPDATED (three diffs)

**Diff 1 — Step 1 (Drain inbox):** rewrites to file only requirement drawer (no 1:1 story shortcut). Body unchanged except removing the "also immediately file a single `story` drawer" line.

**Diff 2 — NEW Step 2 (Spawn a tech-lead):** inserted between Drain and what was Spawn-worker.

```markdown
### 2. Spawn a tech-lead for any undecomposed requirement

`mempalace_list_drawers` wing=`hive` room=`requirements` → find drawers with status ≠ `decomposed`.

If at least one undecomposed requirement exists AND no live agent (tech-lead or worker) currently exists:

- Pick the oldest such requirement (by `created_at`).
- Generate an agent ID (`openssl rand -hex 4`).
- Create `.hive/agents/<id>/`:
  - `context.md` with: agent ID, role=tech-lead, requirement drawer ID + verbatim text, team name (from config).
  - `started_at`, `worker.pid` (after spawn).
- Spawn via Bash:
  ```bash
  nohup claude --print --permission-mode acceptEdits \
    --system-prompt-file "$(pwd)/.claude/skills/tech-lead.md" \
    "You are agent <id>. Read .hive/agents/<id>/context.md and decompose the requirement." \
    > /dev/null 2>&1 &
  echo $! > .hive/agents/<id>/worker.pid
  ```
- File `agent-state` drawer (`role: tech-lead`, `status: live`, `current_requirement: <title>`, `worktree: null`).
- Exit the tick (single-subprocess invariant). Workers spawn on a later tick.
```

**Diff 3 — Step 3 (Spawn worker by role):** replaces the previous spawn-junior step.

```markdown
### 3. Spawn one worker by role

If a tech-lead is currently live this tick (just spawned OR from prior tick), SKIP this step.

Otherwise, find a "ready" story:

- `mempalace_list_drawers` wing=`hive` room=`stories` → all stories
- A story is **ready** iff:
  - `status == pending`
  - For each title in `depends_on`: the story drawer with that title has `status == merged`
  - Empty `depends_on` counts as all deps satisfied
- Pick the oldest ready story by `created_at`.
- Choose role by `points`:
  - 1, 2, 3 → `junior`
  - 5 → `intermediate`
  - 8, 13 → `senior`
- Generate agent ID; create worktree (`git -C repos/<team> worktree add ...`); write `.hive/agents/<id>/context.md` (agent id, role, story title + body + acceptance_criteria, worktree path, branch name).
- Spawn:
  ```bash
  nohup claude --print --permission-mode acceptEdits \
    --system-prompt-file "$(pwd)/.claude/skills/<role>.md" \
    "You are agent <id>. Worktree: repos/<team>--<role>-<id>. Read .hive/agents/<id>/context.md and begin." \
    > /dev/null 2>&1 &
  echo $! > .hive/agents/<id>/worker.pid
  ```
- File `agent-state` drawer (`role: <role>`, `status: live`, `current_story: <title>`, `worktree: <path>`).
- Update story drawer: `status=assigned`, `assigned_to=<id>`.

If NO ready story exists (all pending stories blocked by deps OR no pending stories): no spawn this tick.
```

**Diff 4 — Update Reap step:** existing reap logic stays; small additions:
- On reaping a junior whose story is now `review` (worker opened a PR), check if ALL sibling stories with the same `parent_requirement` are also at `review` or `merged`. If so AND the parent requirement is still `decomposed`, transition it to `in-flight`. If ALL siblings are `merged`, transition parent to `complete`.

**Diff 5 — Tick order:** reordered to drain → reap → spawn (was drain → spawn → reap). Reap-first frees the slot.

**Diff 6 — Diary format:** new format string

## 7. Verification Gate

### Test setup

Same as P1.4 (bare remote + workspace + `hive init`).

### Test requirement

```sh
hive add-req "Add a /healthz endpoint to the test API.
The endpoint must return JSON {\"status\": \"ok\"}.
Include a unit test for it.
Document it in the README under a new ## Health section.
Refactor the existing GET /version handler to share the same response shape."
```

This is crafted to produce stories of mixed sizes:
- Implementation of `/healthz` (likely 2-3 points → junior)
- Unit test for `/healthz` (likely 1-2 points → junior)
- README documentation (likely 1 point → junior)
- Refactor `/version` to share response shape (likely 5 points → intermediate)

A competent tech-lead should emit 4 stories with a clear dependency chain (implementation first; everything else depends on it).

### Phase 2.A PASS criteria

| # | Check | How to verify |
|---|---|---|
| 1 | Manager spawns a `tech-lead` (not a worker) on tick 1 | `ps` shows `--system-prompt-file <wsroot>/.claude/skills/tech-lead.md`; agent-state has `role: tech-lead` |
| 2 | Tech-lead emits ≥ 2 story drawers | mempalace_list_drawers in `stories` room → multiple stories with same `parent_requirement` |
| 3 | Each story has populated `acceptance_criteria` (≥ 1 item) AND `depends_on` (empty OK for root) | Inspect drawers |
| 4 | Tech-lead emits at least one story sized > 3 points (5 or 8) | At least one story with `points > 3` exists |
| 5 | Requirement drawer flips to `status: decomposed` with `decomposed_into` populated | Inspect requirement drawer |
| 6 | Manager next tick spawns the correct role for the ROOT story (no deps) | session log shows correct skill `--system-prompt-file`; agent-state `role` matches `story.points` band |
| 7 | Manager does NOT spawn a worker for a story whose deps aren't merged | `hive status` shows dependent stories `pending` while root is `assigned` |
| 8 | After root story flips to `review` (PR opened), manager spawns next-ready story | session log shows second worker spawn; correct role for that story's points |
| 9 | The 5-pointer (`refactor /version`) spawns `intermediate`, not `junior` | session log + agent-state |
| 10 | Multi-story sequence runs to completion across multiple ticks | Eventually all stories are `merged` (will require manual PR merge against bare remote); requirement flips to `complete` |
| 11 | Diary entries include the new fields (`pending_reqs`, `ready_stories`, `waiting_stories`) | Read diary drawers |

### Stretch (bonus, not required)

- All PRs are actually opened against the bare remote
- Tech-lead's decomposition is "good" by human eye (sized correctly, acceptance criteria are real)
- The senior role gets exercised at least once (requires a story sized 8+ — may need a deliberately larger test requirement)

### Anti-PASS

- Tech-lead emits exactly one story (defeats the point of decomposition)
- Tech-lead emits stories without `acceptance_criteria` populated
- Manager spawns a worker on a story whose deps aren't merged
- Manager spawns `junior` for a 5-point story (mis-routing)
- Junior commits without verifying acceptance criteria (P2.A's self-check should prevent)

## 8. Open Risks

| Risk | Mitigation |
|---|---|
| Tech-lead emits a cycle in `depends_on` | Skill explicitly warns; manager won't detect — operator sees `hive status` showing N stalled stories. Phase 2.D candidate to add cycle detection in Go. |
| Tech-lead reads only requirement text but the text is too vague (`"rewrite to golang"`) | User-side discipline; the tech-lead skill SHOULD file a finding asking for clarification rather than producing nonsense stories. Add an explicit "if the requirement is too vague to decompose, file a finding and exit" rule to the skill. |
| Story title used as dep identifier breaks on rename | Acceptable for Phase 2.A; titles are stable in practice. |
| Role differentiation in skill prose doesn't actually affect Opus behavior — junior/intermediate/senior all produce the same output | This is the experiment. If verification shows no behavioral diff, we collapse to a single `worker.md` in a later refactor. Worth knowing now. |
| Manager mis-routes a story (e.g., spawns junior for a 5-pointer) due to prose-level ambiguity | The role selection lives in the manager skill — if it mis-routes, the worker will likely file a blocker finding. Detectable via verification. |
| One-subprocess cap means tech-leads and workers serialize; throughput is bottlenecked | This is Phase 2.D's job. Phase 2.A's schema (DAG + ready-query + role-routing) is built specifically to make 2.D's lift small. |
