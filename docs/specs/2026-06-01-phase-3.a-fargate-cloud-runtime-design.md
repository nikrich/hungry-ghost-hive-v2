# Phase 3.A — Fargate Cloud Runtime

**Status:** Scoping spec (NOT implementation)
**Date:** 2026-06-01
**Predecessors:** [Phase 2.C — QA auto-merge](2026-06-01-phase-2.c-qa-auto-merge-design.md), [Phase 2.D — Multi-worker parallelism](2026-06-01-phase-2.d-multi-worker-parallelism-design.md)
**Goal:** Move spawn from local `nohup claude --print` subprocesses to AWS Fargate tasks so the operator can run hundreds of concurrent workers without a local machine being on.

## 1. Summary

Phase 1.x + 2.x landed a local autonomous loop. It works on one laptop, capped by `max_workers` (3-15 realistic), bounded by the laptop being awake. Phase 3.A swaps the runtime backend:

- Each role (tech-lead, junior, intermediate, senior, qa) runs inside a Fargate container instead of a local subprocess
- The watchdog, manager, and mempalace gateway run as always-on ECS services
- State that was on local disk moves to S3 (inbox, agent context, logs) and EFS (mempalace ChromaDB)
- Local CLI (`hive add-req`, `hive status`, `hive merge`, `hive logs`) becomes a thin client over the cloud control plane

**Crucially**: skills (`tech-lead.md`, `qa.md`, etc.) do NOT change architecturally. The MUST/MUST NOT blocks, decomposition logic, role routing, mempalace contracts all stay. Only the spawn primitive in `manager.md` flips from `nohup claude --print` to `aws ecs run-task`. Phase 2.D's parallelism logic, Phase 2.C's QA gate, and Phase 1.5's mempalace bridge are all preserved.

**Cost envelope (rough):**
- Fargate Spot (workers): ~$0.012/worker-hour → $30/day for 100 always-on workers
- Fargate On-Demand (control plane: watchdog + manager + mempalace): ~$5-10/day
- API spend (Anthropic): ~$500-2000/day at 100-worker throughput on Opus
- AWS misc (NAT, ALB, ECR, CloudWatch): ~$5/day
- **Realistic monthly: $15-60k**, dominated by API spend

## 2. Goals / Non-goals

### Goals

- Spawn workers as Fargate Spot tasks; control plane as Fargate On-Demand services
- Always-on operation — watchdog + manager + mempalace survive machine sleep, region outages handled via single-AZ failover only
- 100+ concurrent workers achievable (limited only by Anthropic rate limits and AWS API rate limits, not by local resources)
- Local CLI commands work unchanged from operator's POV (`hive add-req "..."`, `hive status`, `hive merge "..."`) — they become thin RPCs to the cloud control plane
- Per-tick cost meter: each task's wall-clock + token usage attributed to its story, written to the diary
- Gradual rollout: config flag `runtime: local | fargate` lets the same workspace flip between modes during migration

### Non-goals

- Multi-region failover (single region; if us-east-1 goes down, operator notices and waits)
- Horizontal mempalace scaling (single mempalace gateway service; ChromaDB on EFS; sufficient for ~hundreds of workers, not thousands)
- Bring-your-own-VPC (Phase 3.A creates and manages its own VPC; integration with existing infra is Phase 3.B)
- IAM-per-tenant isolation (assumes single AWS account, one set of secrets)
- Spot-interruption handling beyond AWS-native (interrupted worker = story re-pended via normal abandonment flow, no checkpointing)
- Replacing Anthropic OAuth flow — workers MUST use `ANTHROPIC_API_KEY`; OAuth doesn't work headless
- Local-runtime deprecation (local stays a supported config for development and small-scale operation)
- Cost budget enforcement that auto-stops the watchdog (covered separately if needed)

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | Workers + QA on Fargate Spot; tech-lead, manager, mempalace, watchdog on Fargate On-Demand | Workers are interruption-tolerant (story re-pends on abandonment); control plane must not flap |
| 2 | Single Docker image for all worker roles; role determined at task start via env var `HIVE_ROLE` | One Dockerfile, one ECR repo. Each task's `command` overrides set the skill path. |
| 3 | mempalace gateway as ECS Service behind Cloud Map service discovery (`mempalace.hive.local`) | Stable DNS for workers; no ALB cost for internal-only HTTP |
| 4 | mempalace ChromaDB on EFS mounted into the gateway container | ChromaDB needs filesystem; EFS gives persistence across container restarts |
| 5 | `.hive/inbox/` → S3 prefix `s3://<bucket>/<workspace>/inbox/`; `hive add-req` becomes `aws s3 cp` | Operator drops files; watchdog drains via S3 ListObjects per tick |
| 6 | `.hive/agents/<id>/context.md` → S3 prefix `s3://<bucket>/<workspace>/agents/<id>/`; injected into worker container via Fargate task env or sidecar download | Worker container reads context at startup, writes back ended_at on exit |
| 7 | `manager.log` and `watchdog.log` → CloudWatch Logs (one log group per workspace) | Operator tails via `hive logs` which wraps `aws logs tail` |
| 8 | git worktrees stay ephemeral per-container — workers `git clone` the team repo into their container at startup, push, exit | EFS-shared worktrees produce locking nightmares; clone is fast (~5s for typical repos) |
| 9 | Auth: `ANTHROPIC_API_KEY`, `GITHUB_TOKEN`, AWS task role credentials all from Secrets Manager, injected as container env | Standard ECS pattern; rotation handled by Secrets Manager |
| 10 | Spawn primitive: `aws ecs run-task --task-definition hive-<role> --overrides '{"containerOverrides":[{"name":"hive","environment":[{"name":"AGENT_ID","value":"..."},...]}]}'` | Returns task ARN; manager uses ARN as the equivalent of worker.pid |
| 11 | Reap primitive: `aws ecs describe-tasks --tasks <arn-list>` returns lastStatus. STOPPED = exited; manager looks at exitCode for success/abandon | Polled per tick; no need for EventBridge for v1 |
| 12 | Cost meter: each task writes a `cost` finding on exit with `wall_clock_seconds` + `estimated_usd` (Fargate cost) + optional `claude_tokens` if the worker captured it | Attribution per-story enables per-requirement spend reports |
| 13 | Config field `runtime: local | fargate` in `.hive/config.yaml`; manager skill branches on it | Same workspace can develop locally, deploy to cloud; no fork in skills |
| 14 | `hive deploy` builds + pushes worker image to ECR + registers task definitions + ensures cluster + services running | One command idempotent provisioning; subsequent runs only push code changes |
| 15 | Per-workspace ECS cluster; one workspace = one cluster. Multiple workspaces don't share infra. | Simpler IAM, cleaner cost attribution, easier teardown |

### Tick lifecycle (cloud-mode)

1. **Watchdog service** wakes on its tick interval (every 60s).
2. Watchdog calls `aws ecs run-task` for the manager task — gets back a task ARN.
3. Manager task starts, MCP-connects to mempalace via `mempalace.hive.local:8080`.
4. Manager runs the same skill as today (drain → reap → spawn 3a/3b/3c → diary), but each "spawn" is now `aws ecs run-task`, and each "reap" is `aws ecs describe-tasks` + `aws ecs delete-task-definition` cleanup.
5. Workers (per `aws ecs run-task`) start with env `AGENT_ID`, `STORY_TITLE`, etc. Each does `aws s3 cp s3://...agents/<id>/context.md /workspace/context.md`, then `claude --print --system-prompt-file <role>.md "..."`.
6. Worker writes back to mempalace via the gateway, pushes git, opens PR, exits.
7. ECS marks task STOPPED; manager picks it up on next tick's reap.

## 5. State / storage

| What | Was | Now (cloud) |
|---|---|---|
| Inbox files | `.hive/inbox/*.txt` (local fs) | `s3://<bucket>/<workspace>/inbox/*.txt` |
| Agent context | `.hive/agents/<id>/context.md` | `s3://<bucket>/<workspace>/agents/<id>/context.md` |
| Agent PID file | `.hive/agents/<id>/worker.pid` | Task ARN stored in mempalace agent-state drawer; PID concept obsolete |
| started_at | `.hive/agents/<id>/started_at` | Stored in mempalace agent-state; ECS task createdAt is fallback |
| manager.log | local file | CloudWatch Logs group `/hive/<workspace>/manager` |
| watchdog.log | local file | CloudWatch Logs group `/hive/<workspace>/watchdog` |
| Worker stdout/stderr | dropped via `> /dev/null 2>&1` | CloudWatch Logs group `/hive/<workspace>/workers/<role>` |
| mempalace ChromaDB | `.hive/memory/index/chroma/` (local fs) | EFS volume mounted at `/mempalace/chroma/` in gateway container |
| mempalace .md drawer files | `.hive/memory/wings/hive/rooms/` (local fs, written by P1.5 bridge) | EFS volume; bridge still operates inside the gateway container |
| Team git repos | local clones in `repos/<team>/` | Cloned fresh inside each worker container at startup; never persisted |

## 6. Skill changes

### `assets/skills/manager.md` — runtime branching

A new opening MUST clause:

```markdown
- **YOU MUST** read `.hive/config.yaml`'s `runtime:` field. If `local`, use the existing nohup-spawn recipes. If `fargate`, use the `aws ecs run-task` recipes below.
```

Each spawn recipe (3a tech-lead, 3b workers, 3c QA) gains a cloud variant. Example for 3b workers:

```bash
# fargate variant
TASK_ARN=$(aws ecs run-task \
  --cluster hive-<workspace> \
  --task-definition hive-worker-<role> \
  --launch-type FARGATE \
  --capacity-provider-strategy capacityProvider=FARGATE_SPOT,weight=1 \
  --network-configuration "awsvpcConfiguration={subnets=[$SUBNET_ID],securityGroups=[$SG_ID],assignPublicIp=DISABLED}" \
  --overrides "{\"containerOverrides\":[{\"name\":\"hive\",\"environment\":[
      {\"name\":\"AGENT_ID\",\"value\":\"$AGENT_ID\"},
      {\"name\":\"STORY_TITLE\",\"value\":\"$STORY_TITLE\"},
      {\"name\":\"BASE_BRANCH\",\"value\":\"$BASE_BRANCH\"},
      {\"name\":\"TEAM\",\"value\":\"$TEAM\"},
      {\"name\":\"WORKER_ROLE\",\"value\":\"$ROLE\"}
    ]}]}" \
  --query 'tasks[0].taskArn' --output text)
```

The agent-state drawer gains a `task_arn:` field (replaces `pid:`).

### `assets/skills/{junior,intermediate,senior,qa,tech-lead}.md` — no logic change

Workers don't know they're in Fargate. They still read context.md, cd into a working tree, run claude, push git. The container entrypoint (Dockerfile) handles cloning the team repo and downloading context.md from S3 before invoking the skill.

## 7. New CLI commands / changed surface

| Command | Behavior |
|---|---|
| `hive init --cloud --aws-account <id> --region <r>` | Creates ECR repo, ECS cluster, IAM roles, S3 bucket, EFS volume, security groups, secrets stubs. Writes a `cloud.yaml` next to `config.yaml` with all ARNs. Idempotent. |
| `hive deploy` | Builds the worker Docker image, pushes to ECR, registers/updates the 5 task definitions (one per role), restarts the watchdog + mempalace services to pick up the new image. |
| `hive add-req "..."` | Local mode: writes to `.hive/inbox/`. Cloud mode: `aws s3 cp` to the inbox prefix. Same UX. |
| `hive status` | Local mode: reads workspace mempalace via Python bridge. Cloud mode: hits `mempalace.hive.local:8080` via a bastion or SSM session manager. |
| `hive logs [tech-lead|worker|qa|manager|watchdog]` | Local mode: tails `.hive/manager.log` etc. Cloud mode: `aws logs tail /hive/<workspace>/<group>`. |
| `hive merge "<title>"` | Local mode: existing. Cloud mode: invoke a one-off `aws ecs run-task` for a merge container OR add a `merge` MCP tool to the mempalace gateway. (Decision: simpler is the one-off task.) |

## 9. Verification

Three milestones, each gated independently:

**Milestone 1: single-container smoke test (~1 day work)**
- Build worker image locally; `docker run` it against a public GitHub repo with embedded skills
- Verify it can: clone repo, run claude --print, write code, commit, push, open PR
- No AWS yet; just proves the container is functional

**Milestone 2: single Fargate task spawn (~2-3 days)**
- Push image to ECR, create minimal ECS cluster, run task definition
- `aws ecs run-task` with environment overrides; task completes; PR appears on GitHub
- No mempalace yet — agent writes a "would have called mempalace" log line

**Milestone 3: full cloud mode (~1 week)**
- Mempalace gateway containerized + EFS mounted + Cloud Map discoverable
- Manager skill cloud variant runs; spawns 3 workers via run-task
- Each worker connects to mempalace gateway via service discovery
- QA spawn flow exercised end-to-end
- Watchdog as ECS Service with KeepAlive
- Operator runs `hive add-req` from laptop → goes to S3 → gets picked up on next tick → cloud watchdog spawns cloud manager spawns cloud workers → real PR on GitHub
- Operator closes laptop → checks back next day → backlog drained

## 10. Cost + ops

### Per-tick steady-state spend (rough)

For a workspace running 100 concurrent workers continuously:

| Component | Resource | Hourly cost |
|---|---|---|
| 100 worker tasks (Spot, 0.25 vCPU, 0.5 GB) | Fargate Spot | $1.20 |
| 1 manager task (per tick) (0.5 vCPU, 1 GB) | Fargate On-Demand | $0.05 |
| 1 watchdog service (0.25 vCPU, 0.5 GB) | Fargate On-Demand | $0.02 |
| 1 mempalace gateway service (1 vCPU, 2 GB) | Fargate On-Demand | $0.10 |
| EFS storage (50 GB) | EFS Standard | $0.02 |
| S3 storage + ops (1 GB, ~10k ops/hr) | S3 Standard | $0.01 |
| CloudWatch Logs (~1 GB ingestion/hr) | CloudWatch | $0.50 |
| NAT Gateway | EC2 | $0.05/hr + $0.045/GB |
| **Subtotal AWS** | | **~$2/hr → $50/day → $1500/mo** |
| **Anthropic API** (dominates) | Opus 4.7 @ 100 workers × 5 PRs/hr | **$20-80/hr** |

### Ops considerations

- **Cost runaway**: easy to hit $1k/day if Opus pricing × throughput surprises. Add a per-workspace daily budget cap (config field `max_daily_usd`); watchdog checks accumulated `cost` findings each tick and stops spawning new work past the cap.
- **Spot reclamation**: workers can be SIGTERM'd by AWS with 2-min warning. Worker's existing exit flow → story re-pended via normal abandonment. Acceptable as long as retry_count cap (3) isn't exhausted.
- **Cold starts**: first Fargate pull from ECR is ~20-30s for typical container. Subsequent pulls are cached on the host (sometimes). For 100-worker steady state, this is amortized.
- **Region pinning**: us-east-1 only for Phase 3.A. If outage, operator notices via stalled CloudWatch metrics and chooses to wait or re-deploy elsewhere.
- **Secrets rotation**: Anthropic API keys + GitHub PATs rotated manually for now. AWS Secrets Manager rotation hooks are out of scope.

## 11. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Cost runaway > $5k/day | High | Daily-budget cap + CloudWatch billing alarms; require operator to set `max_daily_usd` in cloud config |
| Anthropic API rate limits (TPM/RPM) trigger 429s under load | High | Workers retry with backoff on 429; manager observes failure rate and slows spawn-fill if elevated |
| Mempalace gateway becomes bottleneck (single container) | Medium | Vertical scaling first (bump CPU/RAM); horizontal would need backend swap to DynamoDB or RDS — Phase 3.B |
| ECS RunTask API rate limits at high throughput | Medium | AWS supports ~10 RunTasks/sec per account; for 100 workers spawning every few minutes this is fine; for 1000+ workers may need pre-warmed task pool |
| Worker container can't reach mempalace (security group misconfig) | Medium | Caught in Milestone 3 verification; SG rules tightly scoped |
| Lost AGENT_ID / state on Spot reclamation mid-MCP-write | Low | Mempalace writes are atomic per call; partial-state stories re-pend cleanly |
| Operator local CLI unable to talk to cloud mempalace from laptop | Low | SSM Session Manager port-forward documented in runbook |
| Skill drift between cloud and local runtimes | Medium | Both runtimes consume same `assets/skills/` via embedding; `hive deploy` always rebuilds image with current skills |

## 12. Out of scope (this spec)

- **Multi-region failover** — Phase 3.B
- **Horizontal mempalace scaling / backend swap** — Phase 3.B
- **Self-hosted control plane on EKS** — Phase 3.C (for operators who don't want to manage ECS)
- **Anthropic API key rotation via Secrets Manager hooks** — manual for now
- **Per-tenant isolation (multiple operators sharing infra)** — Phase 3.D
- **Cost-budget enforcement beyond per-workspace daily cap** — Phase 3.D
- **Spot interruption checkpointing** — covered by existing abandonment retry, no special handling
- **Local-mode deprecation** — local stays supported indefinitely for development

## 13. Phase 3 sequencing

- **3.A (this spec)** — Single-region single-tenant Fargate runtime, runs 100 workers
- **3.B** — Mempalace backend scaling (DynamoDB or RDS Postgres) + multi-region read replicas
- **3.C** — EKS variant for operators who want Kubernetes
- **3.D** — Multi-tenant SaaS shape (per-workspace IAM isolation, per-workspace billing)
