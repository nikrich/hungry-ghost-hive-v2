# Phase 2.C — QA Auto-Merge (Minimal)

**Status:** Draft → implementation
**Date:** 2026-06-01
**Predecessors:** [Phase 2.D spec](2026-06-01-phase-2.d-multi-worker-parallelism-design.md), [Phase 2.D verification](../plans/2026-06-01-phase-2.d-verification-runbook.md)
**Goal:** Replace the operator-driven `hive merge` gate with a QA worker that runs the test command and calls `hive merge` automatically. This is the prerequisite for unattended multi-day operation (Phase 2.E).

## 1. Summary

Phase 2.D ships parallel execution but every story stops at `status=review` waiting for an operator to run `hive merge`. Phase 2.C drops in a fourth role — `qa` — that the manager spawns whenever a story is in `review`. The QA worker:

1. cds into the worker's existing worktree
2. Runs the team's configured test command (`go test ./...` by default)
3. On pass: calls `hive merge "<story-title>"` via Bash — same primitive operator was using
4. On fail: files a `finding` drawer + flips story back to `status=pending` with `retry_count++`

With QA in place, the system self-feeds: workers produce → QA verifies + merges → manager unblocks dependent stories → loop. Operator drops requirements into `.hive/inbox/` whenever convenient; the watchdog handles the rest.

**Minimal scope** (this spec): test-command-passes + branch-cleanly-merges is the entire QA bar. No LLM acceptance-criteria judgment, no diff review, no linting, no security scan. Those can layer on later.

## 2. Goals / Non-goals

### Goals
- Stories at `status=review` get auto-merged when `go test ./...` passes against the agent branch
- Test-fail flips story back to `pending` (re-pend) with `retry_count++` so a fresh worker can retry
- Configurable test command per team
- New role `qa` with dedicated slot count (`max_qa`, default 2) — does NOT consume worker slots
- Manager tick handles 3 spawn types in one tick: tech-lead (1 slot), workers (max_workers slots), QA (max_qa slots)

### Non-goals
- LLM-based acceptance-criteria judgment (deferred — minimal scope only checks tests)
- Diff review / code-quality QA (deferred)
- Linter or security-scan integration (deferred)
- QA can't request changes via PR comments (deferred — just re-pend on test failure)
- Conflict resolution during merge (still operator-handled — QA inherits `hive merge`'s refusal behavior)
- Budget cap (per user request — no cap in this phase)
- Multi-day reliability validation (Phase 2.E — separate)

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | QA reuses the worker's worktree (read-only — cd in, test, optionally remove) | Worktree already has the agent branch checked out; saves a clone |
| 2 | QA calls `hive merge "<title>"` via Bash — does NOT re-implement merge logic | DRY; merge primitive already handles git + drawer flip + chroma writeback |
| 3 | New `MaxQA int` config field, default 2 | Separate from `max_workers` so a flood of reviews doesn't starve new worker spawns |
| 4 | New `TestCommand string` per-team field, default `go test ./...` | Hardcoded Go command is fine for the bank demo; non-Go projects override per team |
| 5 | Manager step ordering: 1 drain → 2 reap → 3a tech-lead → 3b workers → 3c QA → 4 diary | QA last so it sees any newly-spawned worker's freshly-`review` state on the SAME tick (after worker exits this tick) — though typically QA spawns the tick AFTER worker exits |
| 6 | QA spawn key: at most ONE live QA per story title | Two QAs on the same story would race the merge; manager checks `live_qa_for_<title>` before spawning |
| 7 | Test-fail recovery: flip story to `pending`, `assigned_to=null`, `retry_count++`, file a `finding` (kind=qa-failure, body=test output tail) | Same recovery shape as P2.A worker-abandonment — uniform retry semantics |
| 8 | After 3 QA failures on the same story (retry_count >= 3): story → `blocked`, escalation filed | Same threshold as worker abandonment |
| 9 | QA worker reads context.md just like workers do; manager writes one per QA spawn | Mirror existing spawn contract |
| 10 | When QA exits with success: story will already be `merged` (because `hive merge` flipped it) — manager just reaps the agent-state | No special-case in manager |

## 4. Data model

No new fields on Drawer. The existing `retry_count` is reused for QA failures (same semantics as worker abandonment).

QA agent-state drawer shape (same as worker, role=qa):
```yaml
type: agent-state
status: live | exited
role: qa
team: <team>
current_story: <story title under review>
worktree: repos/<team>--qa-<id>  # optional — see decision 1
pid: <pid>
started_at: <iso>
ended_at: <iso when exited>
```

QA failure finding shape:
```yaml
type: finding
kind: qa-failure
status: open
story: <story title>
team: <team>
qa_agent: <qa agent id>
test_command: <command run>
test_output_tail: <last 50 lines>
created_at: <iso>
```

## 6. Skill changes

### New: `assets/skills/qa.md`

Compact skill. Procedure:
1. `cat .hive/agents/<id>/context.md` — get story title, team, agent branch, test command, worker worktree path
2. `cd repos/<team>--<role>-<worker_id>` — the worker's worktree already has the agent branch checked out
3. Verify clean: `git status --porcelain` should be empty
4. Verify on right branch: `git rev-parse --abbrev-ref HEAD` == `agent/<team>--<role>-<worker_id>`
5. Run `<test_command>` — capture output + exit code
6. If exit == 0:
   - Run `hive merge "<story title>"` from workspace root — captures pass/fail output
   - On merge success: update agent-state to `exited`/`completed`, diary entry, exit
   - On merge fail (conflict): file `finding` (kind=qa-merge-conflict, body=git output), update agent-state to `exited`/`escalated`, exit (operator picks up the conflict)
7. If exit != 0:
   - Tail the test output (last 50 lines)
   - File `finding` drawer (kind=qa-failure, body=test output tail)
   - Update story drawer: `status=pending`, `assigned_to=null`, `retry_count++`
   - Update agent-state to `exited`/`failed`, diary, exit

### Modified: `assets/skills/manager.md`

Add a new step 3c after 3b (worker spawn-fill):

```markdown

`mempalace_list_drawers` wing=`hive` room=`stories` → filter to stories with `status=review`.
```

## 8. Verification

Two scenarios:

### Smoke test: same bank scenario, autonomous merge

Same `nikrich/hive-v2-demo` repo. New requirement queued. Watchdog runs unattended.

Pass criteria:
1. Tech-lead decomposes → 5-8 stories
2. Workers spawn-fill, write code, push PRs
3. QA spawns for each `review` story automatically
4. QA runs `go test ./...`, calls `hive merge`, PRs auto-merge on GitHub
5. Operator never touches `hive merge`
6. All stories eventually reach `status=merged`
7. Parent requirement transitions to `status=complete`
8. New diary fields present: `live_qa=N/max_qa review_stories=N`

### Failure-path test: deliberately broken acceptance

Queue a requirement with a test condition the worker can't satisfy (e.g., "make TestThatAlwaysFails fail" — adversarial). Pass criteria:
1. Worker writes the code, pushes PR
2. QA runs tests, sees failure
3. QA files a `finding` (kind=qa-failure) with test output
4. Story flips back to `status=pending` with `retry_count=1`
5. Manager re-spawns a worker on the now-pending story (same loop)
6. After 3 retries, story → `status=blocked`, escalation filed

## 9. Out of scope

- Phase 2.E reliability rails (separate spec)
- LLM acceptance-criteria judgment
- Test-output-aware retry hints (e.g. "the test expects X, you returned Y" → worker sees this on retry)
- QA-issued PR comments
- Multi-language test command dispatch
