# Phase 2.F — Multi-Team Requirements

**Status:** Scoping spec (NOT implementation)
**Date:** 2026-06-01
**Predecessors:** [Phase 2.A — tech-lead + worker roles](2026-05-30-phase-2.a-tech-lead-and-worker-roles-design.md), [Phase 2.C — QA auto-merge](2026-06-01-phase-2.c-qa-auto-merge-design.md), [Phase 2.D — multi-worker parallelism](2026-06-01-phase-2.d-multi-worker-parallelism-design.md)
**Goal:** A single requirement can decompose into stories that span multiple teams (different git repos), each merged independently against its team's feature branch.

## 1. Summary

Today: one requirement → one tech-lead → one team's feature branch → all stories land in that team's repo. The `team:` field on each story exists but is always set to `teams[0]` from `.hive/config.yaml`. So "Build a payments feature" can only touch the backend OR the frontend OR the docs — not all three from one requirement.

Phase 2.F lifts the per-team pinning by keeping one tech-lead but letting it emit stories with different `team:` values from a single decomposition pass. Each (team × requirement) pair gets its own feature branch on that team's bare remote. Workers + QA already route per-team via the story's `team:` field, so they need zero changes.

Concretely: "Build a payments feature spanning the bank API + the dashboard + the docs" becomes one requirement → one tech-lead spawn → 8 stories where 3 are `team: bank`, 3 are `team: dashboard`, 2 are `team: docs`. The tech-lead creates `feature/payments-feature` on **each** of the 3 teams' bare remotes. Workers fork the right worktree off the right remote's feature branch. QA merges each story into its team's feature branch. After all stories merge, operator merges 3 feature branches into 3 mains (or hive auto-suggests it).

**Backwards compatibility:** existing single-team requirements continue to work unchanged. The requirement drawer's `teams: []` field defaults to `[teams[0]]` when absent.

## 2. Goals / Non-goals

### Goals

- One requirement can produce stories spanning N teams (N ≤ number of teams in `.hive/config.yaml`)
- Tech-lead chooses which teams to touch based on requirement text + per-team descriptions
- Operator can constrain teams via optional `hive add-req --teams team1,team2 "..."` flag
- One feature branch per (team × requirement); same slug across teams for traceability
- Cross-team `depends_on:` works: a story can wait for a story in another team to reach `status=merged`
- QA + worker spawn-fill loops are team-aware: each team's slots fill independently up to `max_workers` (or shared pool — see decision #6 below)
- `hive merge` works unchanged (already routes by `story.team`)
- Per-team test commands respected (already works via Phase 2.C)

### Non-goals

- **Cross-repo integration tests** (Phase 3.C territory — a QA role that can test against multiple repos simultaneously)
- **Per-team tech-lead role** (Option A from the brainstorm — bigger change, deferred indefinitely)
- **Architect role above tech-lead** (Option C from the brainstorm — out of scope; only useful when team count >> 5)
- **Auto-PR for cross-team integration** (operator still merges each feature branch to its team's main individually)
- **Cross-team rebase / sync** (if a story in repo A modifies an API contract, the story in repo B that depends on it still has to discover the change via acceptance criteria — no automatic propagation)
- **Per-team max_workers** (use one shared `max_workers` cap, not N caps; see decision #6)
- **Dynamic team discovery** (workspace config is the source of truth — no scanning github orgs)

## 3. Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | Single tech-lead role + slot (unchanged from P2.D). Tech-lead handles cross-team decomposition. | Avoid the architect-role complexity until team count justifies it |
| 2 | Story's `team:` field is THE routing key. Tech-lead sets it per story; everything downstream reads it. | Schema already supports this — just stop pinning |
| 3 | One feature branch per (team × requirement). Slug derived from requirement title, same string used on each touched team's remote. | Symmetric, easy to grep, easy to merge at the end |
| 4 | Requirement drawer gains `teams: [team1, team2]` field declaring which teams this requirement may touch. Tech-lead is bound by this list. | Operator can constrain; tech-lead can't surprise with off-scope teams |
| 5 | New `description:` field on each team in `.hive/config.yaml`. Tech-lead reads all team descriptions to decide routing. | Tech-lead needs context to make sensible per-story team choices |
| 6 | **One shared `max_workers` cap across all teams** (unchanged). Plus the existing 1 tech-lead slot and `max_qa` QA cap. | Simpler. Per-team caps add complexity for marginal benefit when N teams is small. Phase 2.G can revisit. |
| 7 | Worker spawn-fill loop's "oldest by created_at" rule operates on the union of ready stories across all teams. | Fairness across teams falls out naturally — oldest is oldest regardless of team |
| 8 | Cross-team `depends_on:` works exactly as today — story titles match across teams (titles must be unique within a requirement, but stories in different teams within the same requirement may reference each other's titles) | The status-check loop is already team-agnostic |
| 9 | `hive merge` is unchanged. It reads `story.feature_branch` and `story.team`, operates on `repos/<team>/` — already correct. | Free win from Phase 2.D's design |
| 10 | QA is unchanged. Each story's QA spawn already reads `story.team` and uses that team's `test_command`. | Free win from Phase 2.C's design |
| 11 | `hive add-req --teams team1,team2,team3 "..."` is optional. When omitted, the requirement drawer's `teams:` field is set to ALL teams in config — tech-lead picks freely. | Operator can be lazy or precise |
| 12 | Backward compatibility: requirements without `teams:` in the drawer (legacy P2.D shape) default to `[teams[0].name]` — same behavior as today | Zero migration cost for old workspaces |
| 13 | When a requirement transitions to `status: complete`, manager checks: are ALL stories merged across ALL teams it touched? If yes, complete. If only one team's stories are merged but another team's are still in flight, stay `in-flight`. | Existing transition logic already does this — just operates on a wider sibling set |
| 14 | Tech-lead's "create feature branch" step (P2.D §5) loops over each team in the requirement's `teams:` field, creating the same `feature/<slug>` branch on each team's bare remote. Slug collision check is per-team. | Same slug across teams = grep-friendly; per-team collision check avoids surprises |

## 4. Architecture

The only architectural shift: stories are no longer all-in-one-team for a given requirement. Everything else is identical to Phase 2.D + 2.C.

### Decomposition flow (cross-team requirement)

```
Operator:                                    hive add-req --teams bank,dashboard,docs "Build a payments feature..."
                                                     │
                                                     ▼
Watchdog tick N:        Manager drains inbox  → files requirement drawer with teams: [bank, dashboard, docs]
                                                     │
                                                     ▼
Watchdog tick N+1:      Manager spawns tech-lead with context that includes:
                          - All team names + descriptions from .hive/config.yaml
                          - This requirement's teams: [bank, dashboard, docs] (the bound)
                          - Standard slug computation rule
                                                     │
                                                     ▼
Tech-lead:              Creates feature branch on EACH of bank/dashboard/docs:
                          git -C repos/bank push origin origin/main:refs/heads/feature/payments-feature
                          git -C repos/dashboard push origin origin/main:refs/heads/feature/payments-feature
                          git -C repos/docs push origin origin/main:refs/heads/feature/payments-feature

                        Emits 8 story drawers, each with explicit `team:` value:
                          - "Add /transfers endpoint" — team: bank, feature_branch: feature/payments-feature
                          - "Add transfer history pagination" — team: bank, feature_branch: feature/payments-feature
                          - "Add /transfers IDL request validation" — team: bank, feature_branch: feature/payments-feature
                          - "Build TransferForm React component" — team: dashboard, feature_branch: feature/payments-feature
                          - "Wire TransferForm to /transfers endpoint" — team: dashboard, depends_on: ["Add /transfers endpoint"]
                          - "Add transfer history view" — team: dashboard, depends_on: ["Add transfer history pagination"]
                          - "Document /transfers in api.md" — team: docs, depends_on: ["Add /transfers endpoint"]
                          - "Document TransferForm in user-guide.md" — team: docs
                                                     │
                                                     ▼
Watchdog tick N+2:      Manager spawn-fills: 3 workers, pulled from union of ready stories across all teams.
                          Oldest-by-created_at picks the 3 "Add /transfers" + bank stories first
                          (because tech-leads emit dep-free stories first by convention).
                                                     │
                                                     ▼
Workers + QA loop:      Each worker writes code in its team's worktree (repos/<team>--<role>-<id>),
                        opens a PR against feature/payments-feature on its team's repo.
                        QA spawns per story, runs that team's test_command, calls hive merge.
                        hive merge already targets the right team's bare remote.
                                                     │
                                                     ▼
Cross-team deps:        Dashboard story "Wire TransferForm to /transfers" waits for
                        bank story "Add /transfers endpoint" to reach status=merged.
                        Already works — manager's depends_on=merged check is team-agnostic.
                                                     │
                                                     ▼
After all 8 merged:     Manager transitions requirement to status=complete.
                        Operator now has 3 feature branches (one per team) ready to PR into each main.
                        Phase 2.F does NOT auto-create those final PRs — operator's call.
```

## 5. Data model

### Requirement drawer (additions)

```yaml
---
type: requirement
status: pending | decomposed | in-flight | complete | blocked
title: <verbatim from inbox>
teams: [bank, dashboard, docs]           # NEW — bound on tech-lead routing
decomposed_into: [<story-title>, ...]
feature_branch: feature/<slug>            # SAME slug used across all teams' remotes
created_at: <iso>
---
```

`feature_branch` stays a single string (same slug on each touched team's remote). Story drawers each have their own `team:` + the same `feature_branch:` string.

### Story drawer

```yaml
---
type: story
status: pending | assigned | review | merged | blocked | abandoned
title: ...
team: bank | dashboard | docs            # already exists in P2.A — stops being pinned to teams[0]
points: ...
depends_on: [<story-title>, ...]         # can reference titles in OTHER teams within same requirement
acceptance_criteria: [...]
parent_requirement: ...
feature_branch: feature/<slug>            # same string across all teams in the requirement
pr_url: ...
merged_at: <iso>
---
```

No schema change to the story drawer — only the routing field that's already there gets used.

### Team config (additions)

```yaml
# .hive/config.yaml
teams:
  - name: bank
    repo_url: https://github.com/nikrich/hive-v2-demo.git
    repo_path: repos/bank
    test_command: go test ./...
    description: |                       # NEW — used by tech-lead to decide story routing
      Backend Go HTTP service. Owns: account management, ledger, transfers,
      idempotency, auth. Does NOT own UI or docs.
  - name: dashboard
    repo_url: https://github.com/nikrich/hive-dashboard.git
    repo_path: repos/dashboard
    test_command: npm test
    description: |
      React + Vite frontend. Owns: user-facing UI components, charts, forms,
      account screens. Calls the bank API but does NOT own it.
  - name: docs
    repo_url: https://github.com/nikrich/hive-docs.git
    repo_path: repos/docs
    test_command: vale --no-exit content/
    description: |
      User-facing documentation site. Owns: api.md, user-guide.md,
      runbooks. References bank + dashboard but does not modify them.
```

`description:` is optional; absence → tech-lead has no per-team guidance and will probably make worse routing decisions.

## 6. Skill changes

### `assets/skills/tech-lead.md`

**Context.md template grows** to include all team descriptions and the requirement's allowed `teams:` bound. New step inserted between current step 1 (Decompose) and step 1.5 (Create feature branch):

```markdown
### 1a. Determine team routing per story

Your context.md lists:
- The requirement's `allowed_teams: [...]` (the bound — you may NOT emit stories with `team:` outside this list)
- All teams from `.hive/config.yaml`, including their `description:` field

For each story you plan to emit, pick the right `team:` based on:
- What part of the system the story changes (file paths, file types, build commands)
- Each team's `description:` field

If a story doesn't obviously belong to any team, that's a sign the requirement is mis-scoped — file a `finding` drawer (kind=routing-ambiguous) and ask the operator to clarify which team owns the affected code.
```

Step 1.5 (Create feature branch) now loops over each team in `allowed_teams`:

```markdown
For each team T in `allowed_teams`:
  - Check for collision on T's bare remote: `git -C repos/T ls-remote --heads origin "feature/<slug>"`
  - If collision: append -2/-3/... until unique (use the same suffixed slug across ALL teams for symmetry)
  - Create on T's bare remote: `git -C repos/T push origin origin/main:refs/heads/feature/<final-slug>`

Record the final slug (same string for every team). Every story drawer's `feature_branch:` is this slug regardless of the story's team.
```

Step 2 (Emit stories): no new fields, but the `team:` field now varies per story (previously hardcoded from context).

Step 3 (Update requirement drawer): now writes `teams: [list of teams the emitted stories actually touched]` in addition to `status: decomposed`, `decomposed_into:`, and `feature_branch:`.

### `assets/skills/manager.md`

**Drain step** writes the requirement drawer with `teams:` from either:
- The operator-supplied `--teams` flag if present in the inbox file's frontmatter
- Or all teams from `.hive/config.yaml` if absent (tech-lead picks freely within the full set)

**Spawn-fill loop (step 3b)** is unchanged in logic. It already operates on `mempalace_list_drawers` over the stories room — that returns stories regardless of team. The role-routing table already uses `story.points`. The new behavior is that consecutive iterations of the loop may spawn workers in different teams' worktrees, naturally.

**QA spawn (step 3c)** is unchanged. Per-story team routing already works in Phase 2.C.

**Reap step** is unchanged.

### Worker skills (junior/intermediate/senior/qa)

Zero change. Workers don't know they're part of a multi-team requirement; they just see their team in `context.md`.

## 7. CLI changes

| Command | Change |
|---|---|
| `hive add-req "..."` | Unchanged for single-team use. New `--teams team1,team2,...` flag binds the requirement to a subset of teams. When absent, all teams are allowed. |
| `hive add-req --teams bank,docs "Document the /transfers endpoint"` | New form — explicit scoping. |
| `hive status` | Output gains a per-team breakdown when more than one team is in config: `bank: 3 stories (2 merged, 1 review)`, `docs: 1 story (0 merged, 1 pending)` |
| `hive merge "<title>"` | Unchanged — already routes via `story.team`. |
| `hive logs` | Unchanged — manager.log + watchdog.log are still single-stream. |

The inbox file format gains an optional YAML-frontmatter prefix:

```
---
teams: [bank, dashboard, docs]
---
Build a payments feature spanning the bank API, the dashboard UI,
and the user-facing docs.

Each story should clearly belong to exactly one team based on the file
paths it changes...
```

When the inbox file has no frontmatter (current shape), the manager treats it as the legacy single-team form: `teams: [teams[0].name]`.

## 9. Verification

Two scenarios:

### Smoke test: 2-team requirement, no cross-team deps

Create a 2nd repo (`gh repo create nikrich/hive-v2-demo-frontend --public`) with a minimal Vite scaffold. Add it as a 2nd team in `.hive/config.yaml`. Queue:

```sh
hive add-req --teams bank,frontend "Add a /healthz UI badge:
1. bank: ensure /healthz returns a uptime_seconds field in the JSON response
2. frontend: add a top-bar component that fetches /healthz and shows green/red"
```

PASS criteria:
- Tech-lead creates `feature/<slug>` on BOTH bank's and frontend's bare remotes
- 2 stories emitted, one per team
- Manager spawn-fills both workers in the same tick (using shared cap, different teams)
- Each worker pushes its commit to its team's repo
- QA tests pass per-team (go test for bank, npm test for frontend)
- 2 PRs auto-merged via QA
- Requirement → `status: complete` after both merge

### Cross-team-deps test

```sh
hive add-req --teams bank,frontend "Add the transfer history endpoint and its UI:
1. bank: add GET /accounts/{id}/transfers returning a JSON array of past transfers
2. frontend: add a TransferHistoryTable component that fetches and renders /accounts/{id}/transfers"
```

PASS criteria:
- Tech-lead emits 2 stories where frontend's `depends_on: ["Add GET /accounts/{id}/transfers"]`
- Manager spawns bank worker first (oldest ready story)
- Frontend story stays pending until bank PR is merged by QA
- After bank merges, manager spawn-fill picks up frontend story
- Frontend QA merges; requirement → complete

## 10. Risks

| Risk | Mitigation |
|---|---|
| Tech-lead misroutes stories to wrong team | Per-team `description:` fields make this less likely; routing-ambiguous finding gives operator a feedback channel |
| Slug collision across teams (rare but possible if two requirements at the same time pick the same slug) | Per-team collision suffix — `feature/payments-feature-2` on team B even if team A had `feature/payments-feature` free |
| Cross-team dependency stalls indefinitely (bank story blocked → frontend never starts) | Existing P2.A escalation: if blocking story has `retry_count >= 3`, it goes to `blocked`, dependents stay `pending` forever — operator sees this in `hive status` and resolves |
| Shared max_workers means a flood of bank stories starves the frontend | Acceptable tradeoff for v1; fairness is oldest-first, so frontend stories created earlier still get slots. Per-team caps in 2.G if this bites. |
| Operator forgets `--teams` flag → requirement opens up to all teams → tech-lead routes to teams the operator didn't intend | When `len(config.teams) > 1` AND `--teams` is absent, emit a warning to stderr at `hive add-req` time |
| Tech-lead context.md grows large (N team descriptions) | Keep team descriptions ≤200 words each; operator manages this in config |
| Cross-repo integration breakage (bank API changes, frontend assumed old contract) | Out of scope. Operator's responsibility to write acceptance criteria that specify the contract precisely. Phase 3.C's integration QA worker is the proper fix. |

## 11. Out of scope (this spec)

- Per-team `max_workers` slot allocation (Phase 2.G if needed)
- Cross-repo integration tests (Phase 3.C)
- Per-team tech-lead role (Option A from brainstorm — not justified at small N)
- Architect role above tech-lead (Option C — not justified at small N)
- Auto-PR for final feature-branch → main on each team's remote (operator does it; could be `hive ship "<requirement-title>"` in a future phase)
- Dynamic team discovery (workspace config stays the source of truth)
- Per-team budget enforcement (Phase 3.D if needed)

## 13. Open questions

1. **Tech-lead skill bloat**: at N=5+ teams, the team description block in context.md gets large. Should team descriptions live in their own files (`.hive/teams/<name>.md`) referenced by config? Defer until N forces it.
2. **`hive ship` command**: a one-shot "merge all team feature branches for requirement X into their respective mains" could be a useful operator helper. Not blocking; out of scope here.
3. **Requirement-status visibility**: should `hive status` show per-requirement breakdown (which teams it touched, % merged per team)? Probably yes, but a UI question for the operator. Defer to status-output redesign.
